## 1. Why selection is finished on P2 (stored data, no GPU)

On the 100 main rows of the v22 confirmation (seed 45):

| pool | right answer present | selected (PRM) |
|---|---|---|
| C5 (5 plain samples) | 82 | B5 78 |
| C5 + Q5 (plus the Reader view) | 91 | B10 81 |
| every stored sample | 95 | |

- **The right answer is usually already generated.** The loss is in selection.
- **The tie rule is already hard to beat.** On 57 rows the right answer sits in a PRM top tie with a wrong one. The v22 rule (plain first, then highest last-step reward) is right on 48 of them, i.e. **84% of the disputes**. A new tie-breaker gains a row only if it beats 84% on those disputes. Vote-type rules drop B10 to 74-77.
- **The lost ties are explicit misreadings, and the PRM scores them 1.0.** Examples: "Since there are 2 groups" when the text says "These 3 groups" (p2_1250, 1268, 1263); the absent players counted as leaving; "30 minutes ... in the first hour" (p2_56); the return trip taken as 42 minutes (p2_734).
- **Why no judge fixes this.** v27 showed the PRM hardly reads the problem (r = 0.93 between rewards under the real and the familiar version). v24/v25 showed the same-family Reader recites too.

Two more selection ideas were killed on stored data before being built:
- **The Solver's likelihood ratio against the prototype** as a tie-breaker. The lost ties USE the twist wrongly rather than ignore it, so it would fix at most 1-2 of the 9.
- **A verified memory of same-template problems.** 86/100 rows have a dev sibling, but only 6 of the 22 B5 errors have a confident right sibling, and 2 of those (p2_338, 323) are defective golds.

## 2. The published idea and its open window

- **Context-DPO** (Bi et al., ACL Findings 2025, arXiv 2412.15280). DPO that prefers a "faithful" answer, which follows a counterfactual context, over a "stubborn" one, the model's memorised answer. Its Limitations restrict it to "specific knowledge conflict scenarios": factual QA, single- and multi-hop.
- **Recitation over Reasoning** (RoR-Bench, arXiv 2504.00509). The same conflict in procedural form: a memorised solution schema overrides a modified condition. The authors tried only prompts (a "strictly follow the literal meaning" notice, modified-problem few-shots), got +3 to +12 points, and call it "far from satisfactory ... a more complete solution is still yet to be proposed".
- **MATH-Perturb** (arXiv 2502.06453). Proposes no fix; it "call[s] for research efforts".
- **v26 in this thesis** already tried the knowledge-conflict literature's DECODING-time answer (CAD). Its truncation removed the low-probability branches where the right solutions of the hard rows live (hard rows −9.2 pp). DPO is the TRAINING-time counterpart: it moves probability mass and truncates nothing at inference.

**The evolution v28 tests:** Context-DPO for a procedural conflict, in multi-step math, with the stubborn response generated by the system itself. The Prototype agent rewrites the problem into its familiar version, and the Solver's own solution of that version is the negative. No oracle "original problem" and no human is involved.

Not new: DPO, LoRA, the DPO+NLL loss (Iterative RPO, Pang et al. 2024), self-generated preference pairs.

## 3. The method

| | |
|---|---|
| prompt | the problem, in the CoT prompt every earlier sample was drawn with |
| chosen | a right solution of the problem (a stored sample, graded against gold on the training fold) |
| rejected, **FV** (the method) | the Solver's own solution of the familiar version x0, whose answer is wrong for the real problem: the recited response |
| rejected, **RW** (control) | a stored wrong sample of the real problem |

- **FV and RW are matched.** Same rows, same chosen texts, same number of pairs (up to 2 chosen × 2 rejected per row). Only the rejected text differs, so FV − RW isolates the familiar-version construction.
- **Loss:** DPO (β = 0.1) + 1.0 × the mean token NLL of the chosen response.
- **Adapter:** LoRA r = 16, α = 32, dropout 0.05 on q, k, v, o, gate, up and down, over the 4-bit Solver (bf16 compute).
- **Optimisation:** AdamW, lr 1e-4 with 10% warm-up then linear decay, 2 epochs, 4 pairs per optimizer step, gradient clip 1.0.
- **Reference:** the same model with the adapter disabled.

## 4. The screen

**Rows.** The 200 GSM-Symbolic P2 main rows that have 5 stored plain samples (v21 seed 44 + v22 seed 45, 49 templates), plus the 60 GSM-Plus distractor rows of the same runs as a guard.

**Folds by template.** The 49 templates are split into two folds (seed 28; 99 and 101 rows). Worker *w* trains on fold *w* and samples the rows of the other fold. So every main row is scored exactly once, by a model that never saw any instance of its template. This tests transfer to twists it was not trained on, not memorisation of a template.

**Per worker, one T4 each, in parallel:**
1. The Prototype agent writes the familiar version of the v21 training rows. The v22 rows reuse v27's prototypes.
2. The Solver samples each edited prototype twice (the familiar versions).
3. **Validity.** The untouched Solver re-samples 24 scored rows with k = 4 through the new batched sampler.
4. For FV, then RW: build pairs, train, then draw k = 4 on each scored row and k = 2 on the worker's 30 guard rows.

## 5. Pre-registered (frozen 2026-09-30, before any adapter exists)

**Metric.** Per-sample accuracy, paired by row with the row's 5 stored plain samples (BASE). Significance is a two-sided sign-flip permutation test over rows; a template bootstrap is reported.

| | rule |
|---|---|
| VALIDITY | \|re-sampled base − stored base\| ≤ 10 pp on the 48 validity rows, else nothing is read |
| **PRIMARY** | all 200 rows: FV − BASE ≥ +4 pp **and** p < 0.05 → SUPPORTED; ≤ 0 → REFUTED; otherwise INCONCLUSIVE |
| ATTRIBUTE | FV − RW ≥ +2 pp → the familiar-version negatives are what works |
| HARM | guard FV − BASE ≥ −5 pp |
| GO | SUPPORTED and no HARM → fresh confirmation (train on all 200 rows; the v25 seed-48 rows, against a re-sampled base, plus B-k with the PRM) |

**Reported, not decisive:**
- SC@4 against the first 4 stored samples;
- the recitation rate (the share of samples giving the familiar version's answer);
- the hard rows (stored per-sample ≤ 0.4);
- the training curves (reward accuracy, margin, change in the chosen log-prob);
- RW − BASE.

**How the outcomes read:**
- **SUPPORTED + ATTRIBUTE.** The contribution: self-generated familiar-version negatives teach a 7B model to read modified conditions on unseen templates.
- **SUPPORTED without ATTRIBUTE.** DPO on self-generated pairs helps, but the familiar-version construction is not shown to matter. That is useful, not novel.
- **REFUTED with a good training curve.** The adapter learned its training pairs but did not transfer across templates. Recitation would then be template-specific at this data size, which is itself a finding for the RoR open question.

These rows motivated v28, so the screen decides whether a confirmation is worth running. It is not a thesis claim on its own.

## 6. Cost

Estimated per worker, with both running in parallel:

| step | time |
|---|---|
| prototypes | ~15 min |
| familiar versions | ~30 min |
| validity | ~20 min |
| training | ~1-1.5 h per arm (about 26 s per pair on a T4, not yet measured) |
| scoring | ~1.5 h per arm |

That is about 7-8 h in all. Each worker stops at `MAX_HOURS = 8.0`, and everything is resumable (training checkpoints every 8 optimizer steps).

## 7b. How to run (Google Colab, one GPU)

`MAS_SHT_Colab_v28.ipynb` runs the identical screen.

**The steps, in this order:**
1. worker 0 FV
2. worker 1 FV
3. worker 0 RW
4. worker 1 RW

PRIMARY is readable after step 2; ATTRIBUTE after step 4. An A100 (≥ 34 GB) runs the two workers of a step side by side.

**Storage.** Everything goes to `MyDrive/MAS_SHT_v28`: the worker files, the adapters, the training checkpoints and the logs. A session that ends loses at most the last batch, or the last 8 training steps.

**Each session:** Runtime → Run all.
- The tests run every time.
- The smoke runs only in the first session.
- Finished steps exit in seconds.
- The last cell prints the reading, or PARTIAL if steps remain.

**Time.**

| GPU | until PRIMARY | everything |
|---|---|---|
| T4 | ~8-9 h | ~15 h |
| A100 | | ~3-4 h |

On a T4 that means several sessions.

The same commands work anywhere with one GPU:
`python pretest_v28.py --worker W --arms FV|RW --out-dir DIR`, then `--summary-only --out-dir DIR`.

## 8. Risks, stated before the run

- **DPO on long reasoning often gives small gains.** The NLL term is there for that reason, but it is not a guarantee.
- **The data is small.** Roughly 30-55 eligible rows per worker, a few pairs each. A null result could be under-training; the training curves will show whether the adapter learned its pairs at all.
- **Transfer across templates is the real question.** Transfer within a template would be easier, but it would only show that the benchmark's templates can be learned.
- **The prototype artifact is reused from v26/v27.** The technique is new to the thesis.
