\begin{abstract}
Large language models (LLMs) have demonstrated remarkable capabilities across diverse natural language tasks, yet mathematical reasoning remains a persistent challenge.
Single-pass inference frequently yields errors in multi-step arithmetic word problems due to hallucinated intermediate steps, misidentified operands, and sensitivity to irrelevant distractor information.
We introduce \textbf{MAS-SHT} (Multi-Agent Solver with Structured Hypothesis Testing), a framework that decomposes mathematical problem-solving into specialized agent roles: a \emph{Mathematician} (Architect) that produces a formal, self-verified JSON blueprint and a \emph{Programmer} (Engineer) that implements it as sandboxed executable Python code.
When the Programmer fails or produces an answer that disagrees with a zero-shot baseline, a confidence-gated \emph{Critic} agent performs structured peer review of the primary solution, generating a targeted correction and an independent rederivation.
Disagreeing candidates are then resolved by \emph{verification-weighted arbitration}: answer groups are ranked by deterministic, verifiable evidence---independent-derivation votes (executed program, CAS-evaluated blueprint, zero-shot baseline), symbolic verification status, and code-execution support---and an LLM-based \emph{Judge} is consulted only to break exact evidence ties, constrained to select one of the presented candidates rather than emit a free-form answer.
A rule-based process verification layer and a SymPy symbolic solver fallback provide additional robustness against code-generation failures at zero API cost.
We further introduce \textbf{Symbolic Inverse Verification (SIV)}, a deterministic, zero-API-call verification mechanism operating in two complementary layers.
\emph{Layer~1 (Execution Audit)} substitutes all numeric givens into the symbolic blueprint expression and compares the result to the Programmer's answer, detecting execution deviations without any LLM calls.
\emph{Layer~2 (Given Relevance / Implicated-Variable Set)} algebraically inverts the forward equation chain using SymPy: for each given parameter, SIV treats it as unknown and solves backwards from the computed answer, checking whether the declared value is recovered.
We validated this layer with a controlled fault-injection suite (12 synthetic blueprints, 37 single-given corruptions): it reliably separates declared-but-unused (distractor) givens from used ones (100\%) and never misses the truly corrupted given (100\% recall), but---because every blueprint collapses to one scalar equation over all used givens---it cannot isolate a \emph{single} faulty variable once 2 or more are used: precision is exactly $1/n_{\text{used}}$, so it reports an implicated candidate \emph{set} rather than a unique culprit. We state this bound explicitly rather than the stronger claim our earlier design intended.
We note explicitly that SIV operates on the \emph{math$\to$math} layer: it verifies that the Programmer faithfully executed the Architect's blueprint, but cannot detect errors in the \emph{NL$\to$math} translation layer (i.e., a blueprint that models the problem incorrectly will still pass SIV if it is internally consistent).
This scope is complementary to---rather than competitive with---FOBAR \citep{jiang2024fobar}, which applies LLM-based backward reasoning that partially addresses the translation layer but is probabilistic and provides only a binary verdict; SIV provides a deterministic, structured multi-variable diagnostic (implicated-variable set plus validated distractor exclusion) on the execution layer, at zero API cost.
Because our experiments identify blueprint construction as the single performance bottleneck, we further contribute two architectural mechanisms that target it directly: a \emph{two-step chain-of-thought-to-blueprint extraction} stage that converts a model's own free-form derivation into structured givens and equations (recovering the pipeline on reasoning-tuned models that do not natively emit JSON), and \emph{token-level constrained decoding} that grammar-enforces the blueprint schema for locally hosted open-weight models.
These mechanisms, together with multi-provider support (Groq, Google, Hugging Face, Together) and an in-process local-inference backend with 4-bit quantization, allow MAS-SHT to run end-to-end on small open-weight models (e.g., Qwen2.5-7B, Qwen2.5-Math-7B) at zero API cost and without rate limits.
We additionally expose per-component ablation switches (\texttt{enable\_siv}, \texttt{enable\_sht}) that instantiate inspector-off and hypothesis-testing-off variants for controlled attribution of each component's contribution.
We evaluate MAS-SHT on five established benchmarks---GSM8K, GSM-Hard, GSM-Plus, GSM-Symbolic (P2), and SVAMP---under distractor-augmented conditions.
On a challenging mixed-benchmark set, MAS-SHT achieves 56.8\% accuracy with Qwen3-32B via Groq, compared to 5.4\% for the zero-shot baseline---a gain of \textbf{+51.4 percentage points}---while recording zero ``damage'' cases where a correct baseline answer was overwritten with an incorrect one.
A key finding is that when the Programmer successfully generates and executes code, it achieves 100\% accuracy; the entire performance gap is explained by blueprint construction failures.
On a standard GSM8K subset, the framework achieves 100\% accuracy compared to 90\% for the standalone baseline.
On a fully local, open-weight deployment (Qwen2.5-Math-7B, $n{=}150$, GSM8K/GSM-Hard/SVAMP), a first full run exposed a critical flaw isolated to the candidate-\emph{selection} layer---a free-form LLM judge that scored 15\% on the problems it arbitrated while discarding answers that were 42.5\% accurate---which we trace to a specific, independently verifiable bug and repair with a \emph{verification-weighted arbitration} scheme: candidate selection is resolved by deterministic evidence (cross-derivation agreement and SIV verification) with the LLM judge retained only as a constrained tie-breaker. Re-running the identical problem set after this fix raises accuracy from 74.0\% to \textbf{82.7\%} (+8.7 points) with no change to the underlying solvers, and confirms SIV's verification signal directly: SIV-verified answers are 100\% correct (12/12) versus 65.9\% for unverified ones (though 11 of the 12 fall in the degenerate single-given regime, so this figure alone does not yet certify the multi-variable case).
To give SIV genuinely multi-variable material to be evaluated on, a subsequent coverage-oriented phase reweights the benchmark mix toward GSM-Hard (which yields $\sim$2.6$\times$ more genuine blueprints than SVAMP) and assigns an instruction-tuned sibling (Qwen2.5-7B-Instruct) to every parse-critical role while Math-7B keeps the compute roles: SIV audit coverage rises from 37\% to \textbf{73\%} of problems---but end-to-end accuracy collapses to 57.3\%, exposing a second family of selection-layer defects (a pseudo-vote that counted one derivation twice, SIV verification wielded as a standalone override authority, and a fallback that structurally preferred the primary).
v13.0 closes all three with a \emph{do-no-harm invariant}---the system may override its own zero-shot baseline only when at least two honestly independent derivations agree; absent such corroboration the baseline answer is returned verbatim---plus an \emph{audit-triggered blueprint repair loop} that returns SIV's error report to the Mathematician for one re-derivation before the confidence gate.
The v13.0 run measures \textbf{72.7\%} on the deliberately harder mix (86.7\% on its GSM8K/SVAMP portion, above the earlier, easier mix's 82.7\%; 58.7\% on GSM-Hard, above CoT's 56.0\% there), with the invariant's wiring verified exactly: all 51 uncorroborated problems returned the baseline answer verbatim.
Diagnosing the collapse also yields the sharpest field characterization of SIV to date: verification is highly reliable as a \emph{cross-validator} (22/22 correct when the independent baseline agrees) but unreliable as a standalone authority (2/14 when it disagrees)---an empirical confirmation, with field numbers, of the math$\to$math scope boundary stated above.
The MAS-NoSIV ablation then delivers a genuine negative---as an \emph{arbitration} signal SIV is causally neutral (72.0\% vs.\ 72.7\%, McNemar $p{\approx}1$)---whose diagnosis becomes a contribution in itself: SIV's certificate is confounded with problem \emph{difficulty} (on audit-passed rows the certified answer is 71.4\% correct but the baseline on those same rows is 88.1\%), so a verifier's precision must be judged against the baseline's accuracy \emph{conditioned on the certificate}, not the base rate.
Repositioned as an a-priori \emph{compute router}---the free certificate separates baseline accuracy by +26.6 points and gates which problems receive the expensive Critic stage---the same signal yields the track's first above-baseline result: \textbf{75.3\% vs.\ 74.7\%} at 86\% blueprint coverage, with the routing tier's projected gain (+7.1) confirmed by measurement (+6.9).
Finally, auditing the Architect's stored blueprints against the problem texts shows the dominant NL$\to$math defect at 7B scale is not reasoning but \emph{operand transcription}: 35\% of extracted givens appear nowhere in the problem text, and 68\% of those sit one digit from a number that does.
A deterministic, zero-LLM grounding repair (snap a misread operand to the unique text number one digit-edit away; evaluate formula-valued givens; ambiguity abstains) raises blueprint accuracy on the stored pretest blueprints from 28\% to 48\% on the production prompt and to \textbf{60\%} on the best prompt route, breaking zero previously-correct blueprints---projecting the program-aided path to the baseline's level before any selection-layer gain.
The subsequent GPU run confirms the component projections---blueprint accuracy 20.7\%\,$\to$\,40.7\%, primary 50.0\%\,$\to$\,55.3\%, candidate-pool oracle 84.7\%---while the shipped 74.0\% localizes the giveback to one mechanism: on exactly 5 rows a Critic alternative seeded with the primary's own blueprint corroborated it against the baseline (2 wins, 3 losses, the run's entire paired delta).
The two wins ride on fully text-grounded blueprints and all three losses do not, yielding v15.3's closing principle: \emph{agreement between derivations that share a premise counts as corroboration only when the shared premise is externally verified}---measured at \textbf{76.0\% against 74.7\%} with two wins and zero losses, on a re-run whose candidates are byte-identical to the previous one, so the comparison isolates the selection rule alone. We flag the limits of that number rather than lean on it: it is not statistically significant ($p{=}0.50$), and the rule was derived from this problem set, so a fresh seed remains the measurement that would establish its transfer.
\end{abstract}
\noindent\textbf{Keywords:} Large Language Models, Mathematical Reasoning, Multi-Agent Systems, Hypothesis Testing, Chain-of-Thought, Code Generation, Process Verification, Symbolic Reasoning, Backward Verification

\section{Introduction}
\label{sec:introduction}
% ============================================================
Mathematical word problem solving has long served as a benchmark for the reasoning capabilities of artificial intelligence systems.
Unlike factual retrieval or pattern matching, solving a multi-step arithmetic problem requires identifying relevant quantities, selecting appropriate operations, maintaining intermediate state, and arriving at a numerically precise answer.
Large language models (LLMs) such as GPT-4 \citep{openai2023gpt4}, LLaMA \citep{touvron2023llama}, and Gemini \citep{team2023gemini} have achieved impressive performance on benchmarks like GSM8K \citep{cobbe2021gsm8k}, yet error analysis reveals persistent failure modes: hallucinated operations, misidentified operands, fragility to surface-level rephrasing, and susceptibility to distractor information \citep{shi2023gsmsymbolic,li2024gsmplus}.
Two fundamental questions arise.
First, \emph{can decomposing the reasoning process into specialized agent roles reduce error rates compared to monolithic single-pass generation?}
Second, \emph{when the primary solution is uncertain, can structured exploration of alternative solution strategies recover the correct answer efficiently?}
These questions are particularly pressing on \emph{hard} benchmark variants: problems with larger numerical values, additional distractors, symbolic value substitutions, or structural variations that expose the brittleness of zero-shot reasoning.
Our experiments show that on such challenging benchmarks, zero-shot baseline accuracy can drop to near-zero (5.4\%), while the MAS-SHT framework recovers to 56.8\%---demonstrating that structured multi-agent reasoning is not merely incremental but can rescue problems that a powerful model completely fails on alone.
A further key finding clarifies \emph{where} the value lies: when the Programmer agent successfully generates and executes code, it achieves 100\% accuracy on our test set.
The entire performance gap between MAS-SHT and the baseline is therefore explained not by code execution failures, but by \emph{blueprint construction failures}---cases where the Mathematician cannot produce parseable JSON under token budget and complexity constraints.
This pinpoints blueprint construction as the single highest-leverage target for future improvement.
We present \textbf{MAS-SHT} (Multi-Agent Solver with Structured Hypothesis Testing), whose contributions are:
\begin{enumerate}[leftmargin=*,itemsep=3pt]
    \item \textbf{Architect--Engineer decomposition.} A \emph{Mathematician} agent produces a structured JSON blueprint containing identified unknowns, given values, ordered solution steps, Python-syntax equations, a self-verification estimate, and a distractor checklist. A \emph{Programmer} agent translates this blueprint into sandboxed executable Python code. If the Programmer fails after up to three repair attempts, a \emph{SymPy symbolic solver} re-evaluates the same equations with exact rational arithmetic.
    \item \textbf{Symbolic Inverse Verification (SIV).} After the Programmer produces an answer, SIV performs a two-layer deterministic audit at zero API cost.
    \emph{Layer~1 (Execution Audit)} evaluates the blueprint equations forward with all numeric givens substituted, producing a \texttt{blueprint\_answer}, and compares it to the Programmer's output---directly detecting any execution deviation.
    \emph{Layer~2 (Given Relevance / Implicated-Variable Set)} inverts the symbolic equation chain: for each given variable, it solves backwards from the computed answer and checks whether the original value is recovered; \texttt{failed\_givens} lists the implicated variables and the report is passed verbatim to the Critic for targeted repair. A controlled fault-injection evaluation (\Cref{sec:siv}) establishes precisely what this layer does and does not deliver: it never misses the truly inconsistent given (100\% recall) and reliably excludes declared-but-unused distractors (100\%), but does not isolate a single culprit once 2+ givens are used (precision $=1/n_{\text{used}}$)---an honest scope correction from an earlier, stronger claim.
    When the execution audit passes and all solvable givens reconstruct (confidence $\geq 0.90$), SHT is skipped entirely; when inconsistencies are detected, the implicated-variable report is forwarded to the Critic.
    \emph{Known scope limitation:} SIV operates on the \emph{math$\to$math} layer only. It verifies that the Programmer faithfully executed the Architect's blueprint equations, but cannot detect \emph{NL$\to$math} translation errors---i.e., a blueprint that models the problem incorrectly but is internally consistent will pass SIV's execution audit. This distinguishes SIV from FOBAR \citep{jiang2024fobar} (which applies LLM-based backward reasoning and partially addresses the translation layer, but is probabilistic and gives only a binary verdict): the two methods are \emph{orthogonal} and their combination is strictly stronger than either alone.
    \item \textbf{Self-verification in blueprint construction.} The Mathematician mentally traces through its own equations before finalizing the blueprint, storing the estimate in an \texttt{expected\_answer} field. This field is later consumed by the process verifier.
    \item \textbf{Rule-based process verification.} A zero-API-call verification pass cross-checks the generated code against the blueprint (givens consistency, equation variable coverage, answer sanity, expected-answer deviation). On failure, a second SymPy invocation is attempted.
    \item \textbf{Critic-based Structured Hypothesis Testing (SHT).} When the confidence gate detects uncertainty, a \emph{Critic} agent performs structured peer review: it diagnoses likely errors, generates a targeted correction (informed by the SIV fault localization report when available), and independently rederives a solution from scratch. This peer-review design avoids the correlated-error failure mode of naive parallel resampling.
    \item \textbf{Baseline as an active triage candidate.} The zero-shot baseline answer participates alongside the primary and critic-generated alternatives in majority-vote triage, providing an additional independent signal.
    \item \textbf{Verification-weighted arbitration (v12).} Candidate selection is evidence-first: the CAS evaluation of the Architect's blueprint enters the triage pool as a zero-cost candidate (yielding three \emph{independent} derivations---free program, declarative blueprint, zero-shot CoT), answer groups are ranked by deterministic evidence (votes, SIV verification, executed-code support), and the LLM Judge is demoted to a \emph{constrained tie-breaker} that must select one of the presented candidates by index. This redesign is directly motivated by an $n{=}150$ pilot in which a free-form 7B judge scored 15\% on the problems it arbitrated while the answers it discarded scored 42.5\% (\Cref{sec:pilot_diagnosis}).
    \item \textbf{Baseline-anchored selection under a do-no-harm invariant (v13.0).} The system may override its own zero-shot baseline only when at least two \emph{honestly independent} derivations agree on a value (the \{primary, blueprint-eval\} pair counts as one derivation when the execution audit certifies they computed the same equations); with no such corroboration, the baseline answer is returned verbatim at zero additional cost. The invariant was motivated by a second measured selection-layer collapse (57.3\%, \Cref{sec:v13}) and its wiring is verified exactly in the v13.0 run (51/51 uncorroborated problems returned the baseline answer). v13.0 also adds an \emph{audit-triggered blueprint repair loop}: a failed SIV execution audit returns SIV's error-localization report to the Mathematician for one re-derivation before the confidence gate (trigger quality: 80.3\% recall, zero false alarms; fix success: 15.4\%---a distinction we report explicitly).
    \item \textbf{Blueprint-robust construction for non-JSON-native models.} Motivated by our finding that blueprint construction is the sole bottleneck, we introduce two mechanisms that target it directly. (i)~A \emph{two-step chain-of-thought-to-blueprint extraction} stage: when a model emits free-form reasoning instead of JSON (as reasoning-tuned math models such as Qwen2.5-Math and DeepSeek-Math do by construction), the system feeds the model its own worked solution and asks it to convert that derivation into structured givens and equations---a substantially easier task than generating structure \emph{ex nihilo}. (ii)~\emph{Token-level constrained decoding}: for locally hosted models, a JSON-schema grammar enforces a valid blueprint at the token level, with a leading free-text \texttt{reasoning} field that preserves the model's scratchpad while still guaranteeing parseable output.
    \item \textbf{Provider-agnostic execution and local open-weight deployment.} A unified client abstracts five backends---Groq, Google, Hugging Face Inference Providers, Together AI, and an in-process \texttt{local\_hf} backend built on \texttt{transformers}. The local backend supports 4-bit (NF4) quantization and multi-GPU sharding, enabling the entire multi-agent pipeline to run on small open-weight models (1.5B--7B) at zero API cost and without rate limits.
    \item \textbf{Component-level ablation infrastructure.} Pipeline-level switches (\texttt{enable\_siv}, \texttt{enable\_sht}) instantiate MAS-NoSIV and MAS-NoSHT variants from a single code path, permitting controlled attribution of the inspector and the hypothesis-testing stage without duplicating the pipeline.
    \item \textbf{Distractor robustness evaluation.} A configurable hardening mechanism injects 1--3 irrelevant numerical sentences into problem statements, testing model resilience to distractors.
    \item \textbf{Comprehensive multi-benchmark evaluation} on five benchmarks (GSM8K, GSM-Hard, GSM-Plus, GSM-Symbolic P2, SVAMP) across cloud and local open-weight inference backends.
\end{enumerate}

\section{Related Work}
\label{sec:related}
% ============================================================
\subsection{Chain-of-Thought and Step-by-Step Reasoning}
Chain-of-thought (CoT) prompting \citep{wei2022chain} demonstrated that eliciting intermediate reasoning steps substantially improves LLM performance on arithmetic tasks.
Subsequent work refined this through self-consistency decoding \citep{wang2023selfconsistency}, which samples multiple reasoning paths and selects the most common answer via majority voting.
Our confidence gate draws inspiration from self-consistency but operates across \emph{structurally distinct} solution strategies rather than temperature-varied samples of the same approach---a critical distinction that avoids correlated errors, as we discuss in \Cref{sec:discussion}.
\subsection{Program-Aided Language Models}
Program-aided language models (PAL) \citep{gao2023pal} and Program-of-Thought (PoT) \citep{chen2023program} offload computation to a Python interpreter, achieving higher accuracy by eliminating arithmetic errors in intermediate steps.
MAS-SHT adopts and extends this principle: the Programmer generates code constrained by a formal blueprint, reducing the likelihood of semantically incorrect programs.
When code generation fails, a SymPy-based algebraic solver provides arithmetic-guaranteed answers from the same blueprint equations---extending the PAL paradigm with a symbolic safety net.
\subsection{Multi-Agent Frameworks}
Multi-agent debate and collaboration frameworks have shown promise for improving LLM reasoning.
\citet{du2023improving} demonstrated that multi-agent debate among LLM instances improves factual accuracy.
\citet{liang2023encouraging} showed that assigning diverse roles enhances divergent thinking.
\citet{hong2023metagpt} introduced structured role assignment in coding agents, showing that explicit agent specialization reduces downstream errors.
Our Architect--Engineer pattern assigns complementary \emph{functional} roles: the Mathematician is responsible for mathematical formalization and the Programmer for faithful implementation, with their separation enforced at the prompt level.
\subsection{Verification and Self-Correction}
Verification-based approaches train or prompt models to check their own solutions.
\citet{lightman2023lets} introduced process reward models that evaluate each reasoning step.
\citet{weng2023large} explored self-verification through backward reasoning.
A closely related line of work is \textbf{FOBAR} \citep{jiang2024fobar}, which applies backward reasoning for answer verification: given the forward solution, the LLM is prompted to verify whether the original parameters can be recovered by working backwards.
MAS-SHT's Symbolic Inverse Verification (SIV) pursues the same \emph{cycle-consistency} idea but applies it to a different---and complementary---layer of the reasoning process.
FOBAR operates partially on the \emph{NL$\to$math} layer, using the LLM's natural-language reasoning to assess whether the problem was modelled correctly; SIV operates exclusively on the \emph{math$\to$math} layer, using a computer algebra system to verify that the Programmer faithfully executed the Architect's symbolic blueprint.
The two approaches are therefore \emph{orthogonal}: FOBAR is better positioned to catch translation errors (wrong problem model); SIV is better positioned to catch execution errors (correct model, wrong code) and reports a structured implicated-variable set rather than a binary verdict (\Cref{sec:siv} quantifies exactly how far this falls short of single-variable isolation).
Their union is strictly stronger than either alone.
Within SIV's operating scope---the execution layer---three structural advantages arise over a hypothetical LLM-based execution verifier.
First, verification is \emph{deterministic}: given the same blueprint and answer, SIV always produces the same result; there is no LLM sampling noise.
Second, verification is \emph{free}: zero additional API calls are consumed.
Third, SIV is \emph{immune to correlated execution errors}: a model that consistently makes the same code-generation mistake will also make it during verification, whereas SymPy cannot.
Our rule-based process verification component is additionally related to \emph{peer review} frameworks in NLP \citep{gero2023selfeval}, but applied to mathematical derivation: the Critic is explicitly asked to identify the most likely error category before generating corrections.

Several 2025--2026 lines of work are adjacent to individual mechanisms of ours and are worth delimiting precisely.
CAS-guarded, harm-aware selective replacement of answers \citep{guardedrepair2026} and estimation-verified symbolic solving \citep{evoss2025} occupy the same territory as our do-no-harm invariant and \texttt{expected\_answer} check respectively; LLM-based detection and correction of generated equations is developed in EDCIM \citep{edcim2025}, whereas our repair operator is deliberately deterministic and LLM-free.
Adaptive allocation of verification compute at test time is an active area \citep{qu2026adaptive}; our routing differs in that the gating signal is a \emph{free symbolic audit of the intermediate representation} (the blueprint), not a learned scorer over candidate solutions, and in that we measure \emph{why} the naive use of the same signal as an override authority fails (the certificate--difficulty confound, \Cref{sec:v14_routing}).
Digit-level corruption of operands has been used as a synthetic \emph{perturbation} to study error propagation \citep{misinfoprop2025}; our contribution runs in the opposite direction---measuring that such corruptions dominate a real pipeline's translation failures and \emph{repairing} them deterministically against the problem text.
Aligning quantities in the problem text to equation slots is itself classical in pre-LLM template solvers \citep{kushman2014learning}; what is new here is its use as a conservative, abstention-first repair operator over an LLM's intermediate representation, and the measurement that transcription (not modelling) is the binding defect class at 7B scale.
\subsection{Symbolic and Hybrid Solvers}
Recent work has explored hybrid neural-symbolic approaches to improve numerical precision.
\citet{cobbe2021gsm8k} showed that verifier-guided search substantially improves accuracy on GSM8K.
ToRA \citep{gou2023tora} integrates tool augmentation with rationale generation, interleaving code calls with natural language reasoning steps.
Our SymPy fallback occupies a different point: rather than training a verifier or interleaving tool calls, we leverage a deterministic CAS to execute blueprint equations when code generation fails, providing exact arithmetic on correctly formulated equations.
SIV extends this CAS usage to the verification dimension, applying symbolic inversion as a post-hoc execution-fidelity audit.
\subsection{Rate-Limited Free-Tier LLM Evaluation}
Evaluating multi-agent LLM systems under practical inference constraints (free-tier APIs, token budgets, rate limits) is an underexplored engineering challenge.
MAS-SHT is specifically designed to operate within Groq's free tier of 100,000 tokens/day and 12 RPM for 32B-parameter models, using a realistic token estimation heuristic (input characters $\div$ 4 plus $0.35\times$ max output tokens) rather than pessimistic worst-case budgeting that would cause premature budget exhaustion.
\subsection{Mathematical Reasoning Benchmarks}
GSM8K \citep{cobbe2021gsm8k} remains the standard benchmark for grade-school math reasoning.
GSM-Hard \citep{gao2023pal} replaces numbers with larger values.
GSM-Plus \citep{li2024gsmplus} applies systematic perturbations covering digit expansion, distraction insertion, reversing operations, and numerical substitution.
GSM-Symbolic \citep{shi2023gsmsymbolic} introduces symbolic value variations at three complexity levels (main, P1, P2).
SVAMP \citep{patel2021svamp} tests cross-domain arithmetic reasoning with structural variation.
We evaluate on all five benchmarks.

\section{Method}

\subsection{System Overview}
MAS-SHT processes each mathematical word problem through the pipeline illustrated in \Cref{fig:architecture}:
(1)~zero-shot \emph{Baseline} generation,
(2)~\emph{Mathematician} blueprint construction with self-verification, optionally under token-level constrained decoding,
(2b)~\emph{Blueprint recovery}: if construction yields no equations, a single chain-of-thought-to-blueprint extraction call converts the model's own free-form derivation into structured givens and equations,
(3)~\emph{Programmer} program-aided solving (PAL-style: the agent solves the problem directly in sandboxed Python, with the blueprint supplied as a cross-reference rather than as equations to transcribe), with execution and repair loop,
(3b)~\emph{Rule-based process verification} (advisory: it adjusts confidence and annotates the run, but never overwrites the executed answer),
(3c)~\emph{Symbolic Inverse Verification (SIV)}: a two-layer audit comprising a forward execution check (Layer~1) and an inverse implicated-variable/distractor-exclusion check (Layer~2), both using SymPy CAS at zero API cost,
(3d)~\emph{Audit-triggered blueprint repair} (v13.0): if the execution audit fails, the Mathematician receives SIV's error-localization report and one chance to re-derive the blueprint before the gate ever sees the answer,
(4)~\emph{Confidence Gate} evaluation,
(5)~\emph{Critic-based Hypothesis Testing} with SIV-informed targeted correction and independent rederivation, and---if candidates disagree---
(6)~\emph{verification-weighted arbitration}: majority voting over the candidate pool (which includes the CAS-evaluated blueprint answer as a zero-cost vote), then deterministic evidence ranking, with a \emph{constrained} LLM Judge consulted only on exact evidence ties.
Stage~2b and the constrained-decoding option in Stage~2 (both detailed in \Cref{sec:blueprint_recovery}) are the v11 mechanisms that directly target the empty-blueprint failure mode identified in \Cref{sec:results}; the PAL-style Programmer and the arbitration redesign in Stage~6 are the v12 mechanisms that target the selection-layer failure mode identified in the $n{=}150$ pilot (\Cref{sec:pilot_diagnosis}); the repair loop in Stage~3d and the do-no-harm selection invariant inside Stage~6 (\Cref{sec:do_no_harm}) are the v13.0 mechanisms that target the second selection-layer failure mode exposed once blueprint coverage was raised (\Cref{sec:v13}).

\subsection{Stage 1: Zero-Shot Baseline}
\label{sec:baseline}
The baseline agent receives the problem $P$ with a minimal instruction to solve step-by-step and format the final answer as \texttt{ANSWER:~[[value]]}.
It serves two roles: providing a reference signal for the confidence gate (\Cref{sec:confidence_gate}) and acting as a last-resort fallback when the entire multi-agent pipeline fails.
Generation uses temperature $\tau=0.1$; the token budget was 500 in the v9.1 configuration of Experiments~1--2 and was raised to 1024 in v11.2 (\Cref{sec:experiments}) to accommodate the longer step-by-step traces emitted by reasoning-tuned open-weight baselines.
\paragraph{Answer extraction.}
All agent outputs---including the baseline---pass through a three-stage extraction pipeline:
(1)~tagged extraction matching \texttt{ANSWER:~[[value]]},
(2)~last-number extraction scanning for the rightmost numeral (handling comma-separated values and stripping common unit suffixes such as ``dollars'', ``hours'', ``people''), and
(3)~pattern matching for common phrasings (e.g., ``the answer is 42'', ``result is 42'').
\paragraph{Error response guard.}
Before any extraction, an error-response guard (\texttt{\_is\_error\_response()}) checks whether the LLM returned an error string rather than a mathematical answer.
It detects responses prefixed with \texttt{ERROR\_} (covering \texttt{ERROR\_AUTH\_401}, \texttt{ERROR\_RATE\_LIMIT\_DAILY}, \texttt{ERROR\_BUDGET\_EXCEEDED}), HTTP status codes (401, 403, 429, 500--503) embedded in response text, and authentication or rate-limit phrasing.
This guard is applied at every point where a numeric answer is extracted in the pipeline, preventing HTTP codes from being parsed as mathematical answers---a subtle but critical failure mode identified during development.
% ----- 3.3 -----
\subsection{Stage 2: Mathematician Agent (Architect)}
\label{sec:mathematician}
The Mathematician receives the problem $P$ and a structured system prompt specifying a strict JSON output schema with six required fields:
\begin{itemize}[leftmargin=*,itemsep=2pt]
    \item \texttt{unknown}: a natural-language description of the target quantity.
    \item \texttt{givens}: a flat dictionary mapping descriptive variable names (e.g., \texttt{initial\_apples}) to their numeric values. Only values \emph{relevant} to the solution are included; distractors are explicitly excluded.
    \item \texttt{solution\_steps}: an ordered list of natural-language step descriptions.
    \item \texttt{equations}: an ordered list of valid Python-syntax expressions referencing the \texttt{givens} dictionary. The final equation must assign to \texttt{answer}.
    \item \texttt{expected\_answer}: a mental estimate of the numeric answer, obtained by tracing the equations with actual values before output.
    \item \texttt{distractor\_check}: explicit identification of any irrelevant numbers or context present in the problem statement.
\end{itemize}
\paragraph{Self-verification.}
The \texttt{expected\_answer} field serves a dual purpose.
First, the system prompt explicitly instructs the Mathematician to trace through its own equations with actual numbers before outputting the blueprint, and to revise them if the trace disagrees with its intuitive estimate.
This constitutes a within-call self-consistency check.
Second, \texttt{expected\_answer} is consumed downstream by the rule-based process verifier (\Cref{sec:verification}), acting as a cross-check independent of code execution.
\paragraph{Blueprint extraction cascade.}
The raw LLM response undergoes a four-stage extraction cascade:
(1)~direct JSON parsing of the full response after stripping markdown fences (\texttt{```json...```});
(2)~substring extraction by locating the outermost $\{\ldots\}$ brace pair;
(3)~field-level regex for the \texttt{givens} dictionary (\texttt{"\,givens"\,:\,\{...\}});
(4)~field-level regex for the \texttt{equations} array.
Stages 3--4 provide partial recovery even when the top-level JSON is broken.
Generation uses $\tau=0.0$ for maximum determinism. The blueprint token budget was 600 in the v9.1 configuration under which Experiments~1--2 were run; v11.2 raises it to 1536 tokens to eliminate the mid-object JSON truncation that produced empty blueprints under the tighter budget (\Cref{sec:discussion}).
\paragraph{Blueprint retry.}
If extraction yields an empty blueprint (no equations \emph{and} no givens), a single retry is issued using a simplified prompt that requests only the minimal required JSON fields.
In our experiments, this retry recovers approximately 30\% of initially failed blueprint generations.
Despite this mechanism, 37.8\% of problems in the hard-benchmark experiments still resulted in empty blueprint failures, representing the primary bottleneck of the pipeline.
This empirical finding directly motivates the two v11 blueprint-recovery mechanisms---constrained decoding and chain-of-thought extraction---described in \Cref{sec:blueprint_recovery}, which are engaged respectively \emph{before} and \emph{after} this retry. For reasoning-tuned models (\Cref{sec:heterogeneous}) the simplified retry is skipped entirely, since such models re-emit prose rather than JSON and the extraction stage handles them directly.
% ----- 3.3b -----
\subsection{Stage 2b: Blueprint Recovery and Constrained Decoding}
\label{sec:blueprint_recovery}
The results in \Cref{sec:results} establish that the Architect--Engineer pipeline is bottlenecked entirely by blueprint construction: when a valid blueprint is produced, downstream accuracy is essentially perfect.
This bottleneck is most acute for two classes of model that fall outside the cloud 32B regime of our original experiments.
First, \emph{reasoning-tuned math models} (e.g., Qwen2.5-Math, DeepSeek-Math) are reinforcement-tuned to emit free-form chain-of-thought terminating in a \texttt{\textbackslash boxed\{\}} answer, and do not reliably follow a JSON-output instruction.
Second, \emph{small open-weight models} (1.5B--7B) hosted locally lack the instruction-following fidelity to emit schema-valid JSON under a token budget.
We introduce two complementary mechanisms, both targeting the empty-blueprint failure directly.

\subsubsection{Constrained Decoding (Pre-generation Guarantee)}
For locally hosted models (the \texttt{local\_hf} backend, \Cref{sec:heterogeneous}), the Mathematician call can be issued under \emph{token-level constrained decoding}: a JSON-schema grammar is compiled into a token-level acceptor (\texttt{lm-format-enforcer}) and supplied as a \texttt{prefix\_allowed\_tokens\_fn} to the generation loop, so that at every step the model may only sample tokens that keep the output a valid prefix of a schema-conforming JSON object.
The blueprint schema (\Cref{app:schema}) places a free-text \texttt{reasoning} field \emph{first} and marks it required, so the model retains a chain-of-thought scratchpad before it is forced to emit the structured \texttt{givens}, \texttt{equations}, and \texttt{expected\_answer} fields.
This converts ``produce valid JSON'' from a soft instruction the model may ignore into a hard invariant of the decoder.
The mechanism degrades gracefully: if the enforcement library is unavailable or errors, generation proceeds unconstrained and the standard extraction cascade (\Cref{sec:mathematician}) applies.
\paragraph{Status in v11.2.}
Constrained decoding is implemented and remains available on the \texttt{local\_hf} backend, but it is \emph{not engaged} in the v11.2 evaluation configuration: the \texttt{lm-format-enforcer} acceptor is incompatible with the \texttt{transformers} build available in our Kaggle runtime.
Rather than pin an older library version, v11.2 instead selects an instruction-tuned base model (Qwen2.5-7B-Instruct) that follows the JSON-blueprint prompt directly without token-level enforcement, and relies on the extraction cascade (\Cref{sec:mathematician}) and the post-generation CoT recovery below for the residual failures.
We therefore present constrained decoding as a designed, graceful-degradation pathway whose empirical contribution---relative to a strong instruction-following model plus CoT extraction---is left for future work once the library incompatibility is resolved.

\subsubsection{Two-Step Chain-of-Thought Extraction (Post-generation Recovery)}
Constrained decoding is unavailable for API-hosted models and is undesirable for reasoning-tuned models whose strength \emph{is} their free-form derivation.
For these, we recover the blueprint \emph{after} generation.
If both the primary Mathematician call and (where applicable) the simplified retry return no equations and no givens, the system issues a single focused extraction call: it presents the model with the original problem and its \emph{own} worked solution, and asks it to convert that derivation into structured \texttt{givens} (numeric inputs only) and an ordered list of Python \texttt{equations} whose final line assigns to \texttt{answer} (full prompt in \Cref{app:prompts}).
The key insight is one of \emph{task difficulty asymmetry}: extracting structure from an existing correct derivation is markedly easier for a reasoning-tuned model than synthesizing that structure \emph{ex nihilo} from the problem statement.
When extraction succeeds, the recovered blueprint is tagged \texttt{\_extracted\_from\_cot = True} for logging, and the full downstream pipeline---Programmer execution, SIV audit, and SHT---proceeds on genuine, executable material rather than on a degenerate passthrough.
Long derivations are truncated to their setup and conclusion (first and last 1{,}500 characters) so that both the input quantities and the final answer survive the model's context budget.

\paragraph{Last-resort passthrough.}
If extraction still yields no equations (for the \texttt{local\_hf} backend only), a tautological blueprint is synthesized that assigns the last numeral of the reasoning text to \texttt{answer}, tagged \texttt{\_local\_hf\_fallback = True}.
This keeps an answer flowing so the problem is not a total loss, but we treat it as a degraded path: SIV can only trivially verify such a blueprint, and we report these cases separately rather than counting them as genuine blueprint successes.

\paragraph{Relationship to the bottleneck.}
Constrained decoding attacks the bottleneck \emph{before} generation (making malformed output unrepresentable); CoT extraction attacks it \emph{after} generation (rescuing a correct derivation that happened to be unstructured).
Together they extend the regime in which the Architect--Engineer decomposition---and therefore SIV---can operate, from the cloud 32B setting of our initial experiments down to small, locally hosted open-weight models.

% ----- 3.4 -----
\subsection{Stage 3: Programmer Agent (Engineer)}
\label{sec:programmer}
The Programmer receives the original problem $P$ and the blueprint formatted as a structured text block with labeled sections (\textsc{Target}, \textsc{Given Values}, \textsc{Solution Steps}, \textsc{Equations to Implement}, and optionally \textsc{Distractors to Ignore}), produced by a dedicated \texttt{format\_blueprint\_for\_programmer()} function.
\paragraph{PAL-style solving (v12).}
Since v12, the Programmer operates in the program-aided-language-model regime \citep{gao2023pal}: it is instructed to \emph{solve the problem directly} in Python, treating the blueprint as a colleague's draft to cross-check---explicitly, ``if the draft conflicts with the problem, follow the problem.''
Earlier versions instead required the Programmer to transcribe the blueprint's equations verbatim, which coupled the executed answer to the Architect's translation quality: a mistranslated blueprint was faithfully implemented into a wrong program, and SIV's execution audit degenerated into a tautology (the blueprint being compared against its own transcription).
Our $n{=}150$ pilot quantified the cost of this coupling: single-call PAL scored 88.0\% where the blueprint-transcribing pipeline scored 74.0\% (\Cref{sec:pilot_diagnosis}).
Decoupling restores primary-solver quality to the PAL level \emph{and} makes SIV's execution audit a genuine independent cross-check between two separately derived artifacts (free program vs.\ declarative blueprint).
The Programmer's system prompt enforces the following contract:
(1)~begin with a \texttt{givens} dictionary holding the numeric values the Programmer itself extracts from the problem (this convention is what rule-based verification, metamorphic testing, and SIV givens-matching operate on);
(2)~compute the solution step by step from those givens in plain Python;
(3)~store the final result in a variable named \texttt{answer}; and
(4)~print only the final numeric answer.
\paragraph{Sandboxed execution.}
Generated code is executed in a Python sandbox that blocks: \texttt{import os}, \texttt{import sys}, \texttt{subprocess}, \texttt{\_\_import\_\_}, \texttt{eval(}, \texttt{exec(}, \texttt{compile(}, \texttt{open(}, \texttt{file(}, \texttt{input(}, and \texttt{raw\_input()}.
Output is captured via \texttt{redirect\_stdout}, with fallback inspection of the \texttt{answer} and \texttt{result} local variables if no output was printed.
\paragraph{Repair loop.}
If execution fails, the specific error message is appended to the prompt as structured feedback:
\begin{quote}
\small\texttt{[Attempt 1] EXECUTION ERROR: NameError: 'step\_one' is not defined.\\
Check variable definitions.}
\end{quote}
The Programmer is re-prompted up to three times, each with accumulated feedback from all previous attempts.
Different error types receive tailored messages: \texttt{NameError} advises checking variable definitions, \texttt{KeyError} advises checking \texttt{givens} dict keys, and \texttt{ZeroDivisionError} is reported directly.
\paragraph{SymPy symbolic solver (fallback 1).}
When all repair attempts fail and the blueprint contains valid equations, the SymPy computer algebra system directly evaluates those equations.
The solver builds a restricted execution namespace from the \texttt{givens} dictionary, enriched with safe mathematical built-ins (\texttt{ceil}, \texttt{floor}, \texttt{sqrt}, \texttt{log}, \texttt{exp}, $\pi$).
Equations are executed sequentially via Python \texttt{exec}; for expressions that fail (e.g., due to unresolved variable references), the solver extracts the right-hand side, substitutes known values via string replacement, and attempts symbolic evaluation with \texttt{parse\_expr} (using implicit-multiplication transformations).
SymPy performs exact rational arithmetic, so this fallback is free of floating-point errors on correctly formulated equations.
The SymPy answer is assigned a confidence of 0.8 (vs.\ 1.0 for successful code execution), reflecting that correctness is still contingent on blueprint equation quality.
\paragraph{Performance when code succeeds.}
In our hard-benchmark experiments (\Cref{sec:results}), the Programmer successfully generated and executed code in 20 of 37 problems.
Remarkably, \emph{all 20 of these problems were answered correctly} (100\% accuracy).
This implies that the Architect--Engineer decomposition, when the blueprint is successfully constructed, is essentially sufficient for correctness---the full value of the pipeline lies in getting to a valid blueprint.

\subsection{Stage 3b: Rule-Based Process Verification}
\label{sec:verification}
After code execution produces an answer, a zero-API-call rule-based verifier performs four structural checks:
\begin{enumerate}[leftmargin=*,itemsep=2pt]
    \item \textbf{Givens consistency.}
    The \texttt{givens} dictionary is extracted from the code via AST pattern matching (\texttt{ast.literal\_eval} on the matched substring).
    Each key--value pair is compared against the blueprint's \texttt{givens}.
    Missing keys and numeric mismatches (tolerance $10^{-6}$) are flagged as critical issues.
    \item \textbf{Equation variable coverage.}
    For each equation in the blueprint, the left-hand side variable name is extracted and checked for presence in the code string.
    Missing variables indicate that the Programmer omitted or renamed a required computation step.
    \item \textbf{Answer sanity.}
    A negative answer is flagged unless the problem text contains keywords such as ``loss'', ``decrease'', ``debt'', ``below'', ``fewer'', or ``owe''.
    An answer exceeding the largest given value by a factor of $10^4$ is flagged as a magnitude anomaly.
    \item \textbf{Expected-answer cross-check.}
    If the blueprint's \texttt{expected\_answer} field is non-empty and the relative deviation of the code answer exceeds 10\%, a consistency warning is issued.
    The threshold of 10\% accommodates rounding but catches the most common arithmetic errors.
\end{enumerate}
Issues are classified as \emph{critical} (givens mismatch, negative answer, magnitude anomaly) or \emph{minor} (variable coverage gaps, expected-answer deviation).
When critical issues are found, the verifier confidence is reduced to $\max(0.3,\ 1.0 - 0.25 \cdot n_{\text{crit}} - 0.1 \cdot n_{\text{minor}})$.
\paragraph{Advisory role (v12).}
Rule-based verification is \emph{advisory}: it adjusts the reported confidence and annotates the run log, but it never overwrites the executed answer.
Earlier versions attempted a SymPy re-solve of the blueprint on critical failure and \emph{replaced} the Programmer's answer with the result (confidence 0.75).
The $n{=}150$ pilot (\Cref{sec:pilot_diagnosis}) showed this replacement to be a net loss: the SymPy replacements were 33\% accurate while the answers they overwrote were 50\% accurate on the same problems.
The root cause is a changed interpretation under the PAL-style Programmer: a givens mismatch now frequently signals a \emph{blueprint} (translation) error rather than a code error, so re-solving the blueprint amplifies the wrong artifact.
In v12 the blueprint's CAS evaluation instead participates in arbitration as an SHT candidate (\Cref{sec:sht}), where it is weighed against the executed answer rather than silently supplanting it.
\paragraph{Verification in practice.}
In Experiment 1 ($n=37$), the rule-based verifier passed with confidence 1.0 on all 20 problems where the Programmer generated executable code.
This indicates that when code generation succeeds, the generated code faithfully implements the blueprint---the verifier's primary value is as a guard against regressions rather than a frequent corrective mechanism.
% ----- 3.6 -----
\subsection{Stage 3c: Symbolic Inverse Verification (SIV)}
\label{sec:siv}
\subsubsection{Motivation and Operating Scope}

After the Programmer (or SymPy fallback) produces a numeric answer, Symbolic Inverse Verification (SIV) performs a deterministic, zero-API-call audit using SymPy CAS.
SIV operates in two complementary layers targeting different failure modes.

\paragraph{What SIV verifies.}
SIV operates exclusively on the \emph{math$\to$math} execution layer.
It answers the question: \emph{did the Programmer faithfully execute the Architect's blueprint equations?}
Concretely, this covers: (i)~arithmetic deviations between the Programmer's code and the blueprint's symbolic chain; (ii)~ambiguities in the equation structure (non-uniquely invertible chains, multiple roots); and (iii)~unused given variables (declared in the blueprint but absent from the equation chain---potential distractors or missing equations).

\paragraph{What SIV cannot verify.}
SIV cannot detect errors in the \emph{NL$\to$math} translation layer---i.e., whether the Architect's blueprint correctly models the original problem.
If the Mathematician produces a blueprint with wrong equations that are nevertheless internally consistent, Layer~1 of SIV will pass (the Programmer executed those equations correctly) and Layer~2 will also pass (the givens reconstruct from the wrong answer via the wrong equations).
This is an explicit, irremovable scope limitation arising from SIV's design as a math$\to$math verifier.
We document it explicitly in the \texttt{SIVResult.verifies\_translation = False} field (always \textsc{False}) and in the generated fault localization reports.

\paragraph{Relationship to FOBAR.}
FOBAR \citep{jiang2024fobar} uses the LLM itself for backward verification, which gives it partial access to the NL$\to$math layer (the LLM can reason about whether the problem was modelled correctly) but is probabilistic and provides only a binary verdict.
SIV and FOBAR are therefore \emph{orthogonal}: FOBAR targets translation errors; SIV targets execution errors and reports a structured implicated-variable set rather than a binary verdict (\Cref{sec:siv_fault_injection} quantifies this precisely).
Their combination is strictly stronger than either alone.

\subsubsection{Layer 1: Execution Audit (Forward)}

Layer~1 evaluates the blueprint equation chain in the \emph{forward} direction with all given values substituted numerically:
\[
  \texttt{blueprint\_answer} = \phi(g_1, g_2, \ldots, g_n)
\]
where $\phi$ is the closed-form SymPy expression for \texttt{answer} obtained by composing the blueprint equations, and $g_1,\ldots,g_n$ are the declared numeric givens.

The Layer~1 audit then checks:
\[
  \texttt{execution\_audit\_passed} = \left|\texttt{blueprint\_answer} - A\right| < \varepsilon
\]
where $A$ is the Programmer's computed answer and $\varepsilon$ is a combined absolute/relative tolerance ($10^{-6}$ absolute, $10^{-4}$ relative).

\paragraph{Interpretation.}
If \texttt{execution\_audit\_passed = True}, the Programmer's answer is consistent with what the blueprint equations produce when evaluated correctly.
If \texttt{execution\_audit\_passed = False}, the Programmer deviated from the blueprint: the computed answer does not match the forward evaluation of the declared equations, directly indicating a code-generation or execution error.

\paragraph{The tautology property.}
An important consequence of Layer~1 is that when \texttt{execution\_audit\_passed = True}, Layer~2 (inverse reconstruction) is \emph{guaranteed} to pass as well, because the Programmer's answer is the same value that the forward chain produces---and inverting a function to recover its own input is trivially consistent.
This means that in the \texttt{execution\_audit\_passed = True} regime, Layer~2 provides \emph{localization} of which specific given is recoverable, but not independent evidence of correctness.
The genuine diagnostic power of Layer~2 arises precisely when \texttt{execution\_audit\_passed = False}: the inverse reconstruction then identifies which given variable is most inconsistent with the deviating answer, guiding targeted Critic repair.

\subsubsection{Layer 2: Fault Localization (Inverse)}

Layer~2 operates in three steps:

\begin{enumerate}[leftmargin=*,itemsep=2pt]
    \item \textbf{Symbolic chain construction.} Each blueprint equation is parsed by SymPy with given variables treated as symbolic unknowns (e.g., \texttt{Symbol("initial\_apples", real=True)}). Equations are composed symbolically to produce a closed-form expression $\phi$ for \texttt{answer} as a function of all given variables.

    \item \textbf{Per-given inverse reconstruction.} For each given variable $g_i$ with original value $v_i$, all other givens are substituted with their numeric values, reducing $\phi$ to a univariate expression in $g_i$ alone. SymPy's \texttt{solve()} finds all real-valued roots of $\phi(g_i) = A$. All roots are collected and reported (not just the closest to $v_i$, to avoid a circular selection bias). A given is marked \emph{matched} if any root satisfies $|r - v_i| < \varepsilon_{\text{rel}}$ (relative tolerance $10^{-4}$). If multiple roots exist, the result is flagged \texttt{ambiguous = True} and all roots are reported.

    \item \textbf{Unused-given detection.} If a given variable $g_i$ does not appear in the free symbols of $\phi$, it is classified as an \emph{unused given}: declared in the blueprint but not contributing to the computation. These may be legitimate distractors correctly excluded by the Mathematician, or they may indicate a missing equation. SIV reports them in \texttt{unused\_givens} without marking them as failures, since their absence from the chain is ambiguous (correct exclusion vs.\ blueprint omission). This is a change from earlier versions that silently marked unused givens as matched.

    \item \textbf{Confidence and error localization.} Let $s$ be the number of solvable (chain-dependent) givens and $m \leq s$ the number that matched. The SIV localization confidence is $c = m / s$. If $c \geq 0.90$ \emph{and} \texttt{execution\_audit\_passed = True}, the solution is \emph{verified} at the execution level. The \texttt{failed\_givens} list names the implicated variables (\Cref{sec:siv_fault_injection} establishes precisely what this set does and does not identify); \texttt{get\_error\_localization\_report()} formats a diagnostic covering both layers, phrased as ``re-examine equations involving $\ldots$'' rather than naming a single culprit, and forwarded verbatim to the Critic in Stage~5.
\end{enumerate}

\subsubsection{Layer 2 Scope Validation: Controlled Fault Injection}
\label{sec:siv_fault_injection}
Real MAS-SHT runs almost never exercise Layer~2 on a genuine multi-variable blueprint---1 of 150 problems in our local open-weight evaluation (\Cref{sec:pilot_diagnosis})---so its diagnostic scope cannot be established from field data alone.
We validate the mechanism directly with a controlled fault-injection suite (\texttt{test\_siv\_fault\_injection.py}): 12 synthetic blueprints spanning additive, multiplicative, multi-step, and distractor-bearing equation structures (2--5 used givens each), each given a single corrupted variable (holding the rest at their true value) while the target answer is fixed at the true, uncorrupted value---the scenario a PAL-style Programmer that reads the problem independently and correctly would produce.
Across 37 single-variable corruptions, three quantities are measured directly against \texttt{SymbolicInverseVerifier.verify()}, with no LLM involved:
\begin{itemize}[leftmargin=*,itemsep=2pt]
    \item \textbf{Recall} (the truly corrupted variable is always present in \texttt{failed\_givens}): $37/37 = 100\%$.
    \item \textbf{Exclusion} (declared-but-unused distractors are correctly separated from used givens): $12/12 = 100\%$.
    \item \textbf{Exact isolation} (\texttt{failed\_givens} names \emph{only} the corrupted variable): $0/37 = 0\%$ whenever 2 or more givens are used. Mean precision is exactly $1/n_{\text{used}}$: 50\% at $n_{\text{used}}=2$, 33\% at $n_{\text{used}}=3$, 25\% at $n_{\text{used}}=4$, 20\% at $n_{\text{used}}=5$ (isolation is only exact in the degenerate $n_{\text{used}}=1$ case).
\end{itemize}
This is a structural consequence of the design, not an implementation defect: because every blueprint's equations collapse to one scalar expression $\phi(g_1,\ldots,g_n) = \text{answer}$ (\Cref{sec:mathematician}'s schema requires every chain to terminate in a single \texttt{answer} assignment), holding all other givens fixed at their declared values while inverting for one $g_i$ at a time generically shows \emph{every} used variable as inconsistent whenever the forward audit fails---perturbing any single input requires a compensating shift in every other input's reconstructed value to explain the same observed discrepancy, not just the one that was actually corrupted.
We therefore correct our own earlier, stronger claim: Layer~2 is a validated \emph{distractor-exclusion filter} and a validated \emph{implicated-variable superset} (the true fault is never missing), not a point localizer.
The \texttt{get\_error\_localization\_report()} text passed to the Critic (\Cref{sec:sht}) already reflects this---it recommends re-examining a set of equations rather than naming a single erroneous one---and the Critic's targeted-repair benefit should be read accordingly: it narrows the search from ``the whole problem'' to ``these load-bearing variables,'' not to a single named fault.

\subsubsection{Special Cases}

\paragraph{Non-invertible chains.}
Equations involving \texttt{floor}, \texttt{ceiling}, absolute value, or conditional branches may not yield closed-form SymPy solutions.
In these cases, SIV reports \texttt{solvable = False} for those givens and abstains from penalizing the confidence, deferring to the rule-based verifier.
Coverage of the blueprint (what fraction of problems yield a fully invertible chain) is reported in \texttt{invertible}.

\paragraph{Multiple solutions (ambiguity).}
When SymPy returns multiple real roots (e.g., for quadratic equations), all roots are reported in \texttt{all\_real\_roots} and \texttt{ambiguous = True} is set.
A match is declared if \emph{any} root lies within tolerance of $v_i$, but the ambiguity is noted explicitly rather than concealed.
Prior versions selected the root closest to $v_i$, which was circular; the new design is transparent.

\paragraph{Unused givens.}
If a given does not appear in the symbolic chain, it is not solvable by inversion and is reported in \texttt{unused\_givens}.
It does not count toward $s$ (the solvable denominator) and does not reduce confidence.
The Critic prompt explicitly receives this list and is instructed to judge whether exclusion was intentional.

\subsubsection{Integration Points}

SIV integrates at three points in the pipeline:
\begin{enumerate}[leftmargin=*,itemsep=2pt]
    \item \textbf{Post-verification confidence.} If the execution audit passes (\texttt{execution\_audit\_passed = True}), rule-based verification concerns from Stage~3b may be overridden. This prevents the pipeline from discarding an answer that is execution-consistent merely due to minor code-style deviations caught by rule-based checks.

    \item \textbf{Confidence gate (highest-priority criterion, \Cref{sec:confidence_gate}).}
    SIV is evaluated as Criterion~0 in the gate.
    A result with \texttt{execution\_audit\_passed = True} \emph{and} \texttt{verified = True} \emph{and} confidence $\geq 0.90$ triggers a skip of SHT, saving 1--3 API calls.
    \texttt{execution\_audit\_passed = False} triggers a new gate reason (\texttt{siv\_execution\_error}) that activates SHT even when other criteria would pass.
    A result with a non-empty \texttt{failed\_givens} but \texttt{execution\_audit\_passed = True} triggers SHT with localization context.

    \item \textbf{SIV-informed Critic (\Cref{sec:sht}).}
    When SHT is triggered and SIV found specific inconsistencies (either execution error or failed given), the two-layer report is injected into the Critic's prompt as ``Automated Verification Report''.
    Layer~1 tells the Critic whether the Programmer deviated from the blueprint.
    Layer~2 tells the Critic which variables are implicated (\Cref{sec:siv_fault_injection}: reliably the full used-variable set when 2+ givens are involved, not a single named culprit).
    This still narrows the Critic's first alternative from speculative re-derivation into a targeted repair over a smaller variable set, short of pinpointing a unique fault.

    \item \textbf{Audit-triggered blueprint repair (v13.0).}
    An \texttt{execution\_audit\_passed = False} verdict additionally triggers a single blueprint-repair attempt \emph{before} the confidence gate: the Mathematician receives SIV's own error-localization report together with the original problem and gets one chance to re-derive the blueprint, after which the Programmer and SIV re-run on the repaired artifact.
    The trigger is empirically well-chosen: on the mixed-preset diagnostic run (\Cref{sec:v13}), a failed execution audit identified blueprints whose CAS answer was wrong with 80.3\% recall (49/61) and \emph{zero} false alarms on blueprints that were actually correct (0/25)---by far the strongest in-loop repair signal available.
    Its \emph{fix} success is far more modest (6/39 repairs subsequently passed the audit; \Cref{sec:v13} discusses the distinction), so the mechanism is best read as SIV acting as an in-loop repair signal rather than a reliable self-correction step.
    The two extra LLM calls a repair spends are charged to the per-problem call budget, and the attempt is logged in a dedicated \texttt{blueprint\_repaired} field.
\end{enumerate}

\subsection{Stage 4: Confidence Gate}
\label{sec:confidence_gate}
The confidence gate is a deterministic, zero-cost component deciding whether to accept the primary answer or trigger hypothesis testing.
It evaluates criteria in priority order; any single trigger activates SHT:
\begin{enumerate}[leftmargin=*,itemsep=2pt]
    \item \textbf{Programmer failure.} The primary answer is ``unknown'' (all repair attempts and the SymPy fallback failed).
    \item \textbf{Baseline disagreement.} $|a_p - a_b| > 10^{-3}$ (numeric comparison) or string inequality (non-numeric answers). This criterion runs \emph{before} any SIV-driven skip (a v10.1 ordering fix): SIV cannot detect NL$\to$math translation errors, and the baseline is the only translation-layer cross-check available, so a SIV pass must never override a baseline disagreement.
    \item \textbf{Repair exhaustion.} The \texttt{quality\_metrics} dict reports \texttt{error = "Max attempts reached"}, indicating the Programmer produced code but failed to execute it successfully.
    \item \textbf{SIV fault localization.} If the chain is symbolically invertible but one or more solvable givens fail to reconstruct, SHT is triggered. The specific fault localization report is passed to the Critic (\Cref{sec:sht}).
    \item \textbf{SIV execution error.} If \texttt{execution\_audit\_passed = False} (the Programmer's answer deviates from the blueprint forward evaluation), SHT is triggered with reason \texttt{siv\_execution\_error}.
    \item \textbf{Unverifiable negative answer (revised in v12).} $a_p < 0$ \emph{and} the baseline failed. A negative primary that the baseline \emph{agrees} with no longer triggers SHT: two independent derivations concurring on a negative value is evidence, not an anomaly. The pre-v12 unconditional trigger routed every agreed-negative into SHT and was a measurable liability on GSM-Hard, whose golds are frequently negative (pilot: 17\% MAS vs.\ 83\% PAL accuracy on negative-gold problems); a negative that disagrees with the baseline is already caught by criterion~2.
    \item \textbf{Magnitude anomaly.} $|a_p| > 10^4 \times \max_{v \in \text{givens}} |v|$.
    \item \textbf{Baseline failure.} $a_b = $ ``unknown'': with no cross-check available, SHT is triggered out of caution.
\end{enumerate}
If none of the triggers fires, the answer is accepted; when additionally the SIV execution audit passed, all solvable givens reconstructed, and SIV confidence $\geq 0.90$, the skip is recorded as \texttt{siv\_execution\_consistent} (cross-validated by baseline agreement \emph{and} symbolic verification).
In our hard-benchmark experiments, the gate triggered on 94.6\% of problems.
The dominant reason is \textbf{baseline disagreement}: the Programmer's structured pipeline frequently produces a different answer from the zero-shot baseline, which may itself be unreliable on hard benchmarks.
This high trigger rate is not a failure of calibration but a reflection of genuine difficulty---on standard GSM8K, the trigger rate drops to 20\%.

\subsection{Stage 5: Critic-Based Structured Hypothesis Testing (SHT)}
\label{sec:sht}
\subsubsection{Design Rationale: Peer Review over Parallel Resampling}
A naive implementation of multi-hypothesis testing would instruct the same LLM to generate $k$ independent solutions and apply majority voting.
This has a fundamental statistical weakness: when the same model generates all candidates with different random seeds, the errors are \emph{correlated}.
A systematic misconception (e.g., confusing subtraction with division in a rate problem) recurs across all samples, rendering majority voting equivalent to a single draw from a biased distribution.
MAS-SHT addresses this with a \textbf{critic-based} design.
Rather than asking ``generate another solution'', the system asks ``what is wrong with this solution?''
This asymmetric framing forces metacognitive reasoning about failure modes before any correction is attempted.
\subsubsection{Critic Agent}
When the confidence gate triggers, a single LLM call to the Critic performs three tasks:
\begin{enumerate}[leftmargin=*,itemsep=2pt]
    \item \textbf{SIV-informed error diagnosis.} If SIV found specific inconsistencies, the Critic's prompt includes the full two-layer fault localization report (e.g., \emph{``Layer~1: Programmer's answer 120 deviates from blueprint evaluation 80 (rel\_error=0.50). Layer~2: variable \texttt{rate\_per\_hour} reconstructs as 12.0 from the answer, but problem states 8.0---check multiplication step''}). If SIV did not run or the chain was not invertible, the Critic reviews the primary solution against a standard five-point checklist: (a)~correct number extraction, (b)~absence of distractor contamination, (c)~correct mathematical operations, (d)~no missing steps, and (e)~whether the answer addresses the correct question.
    \item \textbf{Targeted correction.} The first alternative blueprint directly addresses the most likely error. Its \texttt{strategy\_name} records the error type (e.g., \texttt{correction\_of\_missing\_steps}, \texttt{correction\_of\_distractor\_inclusion}), providing interpretable diagnostic output. When SIV provides a specific failing variable, this correction is \emph{targeted} rather than speculative.
    \item \textbf{Independent rederivation.} The second alternative blueprint solves the problem from scratch without reference to the primary approach, using \texttt{strategy\_name = independent\_rederivation}.
\end{enumerate}
The Critic outputs a JSON object with a \texttt{review} field and an \texttt{alternatives} array of exactly two blueprints.
Generation uses $\tau=0.3$, permitting variation in error diagnosis while maintaining structural JSON fidelity.
\subsubsection{Baseline and Blueprint as Active Triage Candidates}
Crucially, the zero-shot baseline answer is not merely a gate trigger---it is registered as a triage candidate with a fixed confidence of 0.5.
This means that if both the Programmer's code and the Critic's alternatives fail to execute, the baseline answer can still be selected as the best available answer.
Since v12, the CAS evaluation of the Architect's blueprint (already computed by SIV's execution audit, hence free) also enters the pool as the \texttt{blueprint\_eval} candidate.
With the PAL-style Programmer, the pool thus contains three \emph{independent} derivations of the answer---a free program, a declaratively modeled and CAS-evaluated blueprint, and a zero-shot chain of thought---so agreement between any two of them is meaningful evidence in a way that the earlier two-way primary-vs-baseline standoff was not.
\subsubsection{Alternative Execution}
Each of the Critic's two alternative blueprints is passed to the Programmer for a single execution attempt (no repair loop, to bound API costs).
Combined with the primary answer, the baseline, and the blueprint evaluation, this yields up to five candidates.
\subsubsection{Triage (Majority Voting)}
Candidates are filtered to those with \texttt{code\_success = True} and a non-null parsed numeric answer, then grouped by answer value (tolerance $\epsilon = 10^{-3}$).
Groups are ranked by size, with average confidence as a tiebreaker; since v13.0, ``size'' means \emph{honest} votes---the \{primary, \texttt{blueprint\_eval}\} pair counts as one derivation when the execution audit certifies they computed the same equations (\Cref{sec:do_no_harm}).
Three outcomes are possible:
\begin{itemize}[leftmargin=*,itemsep=2pt]
    \item \textbf{Unanimous}: all valid candidates share a single answer $\Rightarrow$ accepted directly.
    \item \textbf{Majority}: the largest group has $\geq 2$ members and strictly dominates $\Rightarrow$ accepted.
    \item \textbf{No majority}: candidates disagree without a dominant group $\Rightarrow$ escalate to evidence-based arbitration.
\end{itemize}
\subsubsection{Evidence-Based Arbitration (v12)}
\label{sec:evidence_arbitration}
When majority voting is inconclusive, answer groups are ranked by a lexicographic tuple of \emph{deterministic, verifiable} evidence---no LLM call is involved:
\begin{enumerate}[leftmargin=*,itemsep=1pt]
    \item \textbf{votes}: the number of independent derivations agreeing on the answer;
    \item \textbf{SIV verification}: the SIV inverse layer fully verified this answer (execution audit passed, all solvable givens reconstruct, confidence $\geq 0.90$)---evidence beyond the forward blueprint vote;
    \item \textbf{executed code}: the group contains an answer produced by actually executed code (in the pilot, on program-vs-CoT disagreements the executed program was correct in 15/29 cases and the CoT in 4/29);
    \item \textbf{primary support}, then \textbf{baseline support}, as final deterministic tie-breaks.
\end{enumerate}
A strict lexicographic winner is accepted directly (\texttt{triage\_result = evidence}).
Since v13.0, auto-resolution additionally requires the winning group to be \emph{corroborated} (honest votes $\geq 2$); the SIV component of the tuple orders corroborated groups but can no longer qualify a lone group on its own, and a field with no corroborated group at all bypasses arbitration entirely in favor of the baseline (\Cref{sec:do_no_harm}).
\subsubsection{Constrained LLM Judge (Tie-Break Only)}
Only when two or more groups tie on the full evidence tuple is the LLM Judge consulted, and its authority is deliberately narrow: it receives one representative per tied group (strategy name, answer, equations, first 300 characters of code) and must reply with the \emph{index} of one presented candidate (\texttt{SELECTED\_CANDIDATE:~[[k]]}, $\tau=0.0$).
A legacy \texttt{SELECTED\_ANSWER} tag is honored only if it numerically matches a presented candidate.
Any other output---an out-of-range index, a novel number, unparseable text---is rejected, and a deterministic fallback selects the executed primary, then the baseline, then any valid candidate.
The judge therefore \emph{cannot} introduce an answer that no solver produced.
This design is a direct response to the pilot failure analysis (\Cref{sec:pilot_diagnosis}): the pre-v12 judge answered free-form, and when its output tag failed to parse, the last number in its rationale was scraped as the ``answer''---yielding candidate indexes and confidence values as final answers, and a 15\% accuracy on the 40 problems it arbitrated (its own discarded baseline: 42.5\%).
\subsubsection{Baseline-Anchored Selection: The Do-No-Harm Invariant (v13.0)}
\label{sec:do_no_harm}
The mixed-preset run of \Cref{sec:v13} exposed three further selection-layer defects, each measured in that run's log; v13.0 responds by making a single invariant structural:
\begin{quote}
\emph{The system may override its own internal zero-shot baseline only when at least two honestly independent derivations agree on the same value. Absent such corroboration, the final answer is the baseline answer verbatim} (new triage outcome \texttt{baseline\_default}, at zero additional LLM calls).
\end{quote}
Three concrete changes implement it:
\begin{enumerate}[leftmargin=*,itemsep=2pt]
    \item \textbf{Honest votes (pseudo-vote fix).} \texttt{blueprint\_eval} can only land in the same answer group as the primary when the SIV execution audit passed---which \emph{certifies} that the Programmer's code computed those very equations. That is one derivation observed twice, not two independent confirmations, yet both majority voting and the \texttt{votes} evidence component counted it as 2, letting the pair outvote the genuinely independent baseline. Measured: 36 such ``majority'' rows in the mixed run, on which the baseline was right 30/36 while the pair-vote answer was right 24/36. Vote counting now deduplicates the \{primary, \texttt{blueprint\_eval}\} pair everywhere; \texttt{blueprint\_eval} still carries a full vote in any group \emph{not} containing the primary (e.g.\ agreeing with the baseline against a deviant program, where it is genuinely independent).
    \item \textbf{SIV verification is a cross-validator, not an authority.} Measured on the same run: SIV-verified answers were 22/22 correct when the baseline agreed, and 2/14 correct when the baseline disagreed. This is the paper's own scope claim (\Cref{sec:siv}) surfacing in field data---a verification that certifies blueprint-internal consistency inherits the blueprint's translation errors. Full SIV verification therefore no longer auto-resolves the evidence ranking on its own (v12.1 allowed it to); it remains a deterministic tie-breaker \emph{between already-corroborated groups}, and the same gating was applied to a second, previously unnoticed instance of the same bug (the v11.4 SIV-anchor override late in \texttt{solve()}, now suppressed whenever a live baseline disagrees). The confident-skip gate is untouched: it always required baseline agreement before any SIV skip (\Cref{sec:confidence_gate}) and remained 97.9\% accurate on the mixed run.
    \item \textbf{Uncorroborated fields go to the baseline, not the judge.} When no group reaches two honest votes, the judge is not consulted at all: no LLM judge in any of our runs has extracted signal from a field of lone, unverified candidates (free-form pilot judge: 15\%; constrained v12.1 judge on the mixed run: 0/55 outputs parseable, because the Math-7B judge wrote chain-of-thought until its token cap and never reached the tag). The judge prompt is now \emph{tag-first} (\texttt{SELECTED\_CANDIDATE:~[[k]]} must be the first line, \Cref{app:prompts}) so truncation cannot destroy the tag, the judge is retained only for ties between corroborated groups, and the deterministic fallback on judge failure now prefers the baseline---the old primary-first fallback was the v12.1 coin-flip bug's twin living in the one function that fix never reached, and it fired 55 times on the mixed run at 8/55 accuracy against the discarded baseline's 29/55.
\end{enumerate}
All three changes were verified offline before any GPU run: 33 simulation checks built on real \texttt{SymbolicInverseVerifier} and \texttt{HypothesisResult} objects (no models, no network) cover every branch, and a counterfactual replay of the collapsed run's own rows under the new rules projected 75.3\%.
\Cref{sec:v13} reports the subsequent measurement.

\subsection{Heterogeneous Model Configuration}
\label{sec:heterogeneous}
MAS-SHT supports assigning different LLMs to different agent roles via an \texttt{AgentRole} enum (\textsc{Baseline}, \textsc{Mathematician}, \textsc{Programmer}, \textsc{Hypothesis\_Generator}, \textsc{Judge}) and a \texttt{ModelConfig} dataclass specifying a provider, a model name, and a \texttt{load\_4bit} flag.
A single \texttt{UnifiedLLMClient} abstracts five backends behind one interface:
\begin{itemize}[leftmargin=*,itemsep=1pt]
    \item \textbf{groq} and \textbf{google}: cloud APIs (Qwen3-32B, LLaMA~3.x, Gemma, Mixtral; Gemini), each with a dedicated rate limiter.
    \item \textbf{huggingface}: the Hugging Face Inference Providers Router (OpenAI-compatible), which transparently routes a model to an available serverless host and handles 503 cold-starts with exponential backoff.
    \item \textbf{together}: Together AI's OpenAI-compatible endpoint, a practical host for serverless 7B math models.
    \item \textbf{local\_hf}: an in-process backend built on \texttt{transformers.AutoModelForCausalLM}, loading weights directly onto the local GPU(s). It incurs \emph{zero} API cost and \emph{no} rate limit, and is the backend used for our small open-weight evaluation.
\end{itemize}
\paragraph{Cloud presets.}
Five cloud presets cover the homogeneous and heterogeneous regimes: \textit{homogeneous\_groq} (all roles Qwen3-32B), \textit{diverse\_groq} (LLaMA~3.3~70B for structured roles, Gemma~2~9B baseline, Mixtral~8$\times$7B critic), \textit{cross\_provider} (Groq LLaMA~70B $+$ Google Gemini), \textit{budget\_optimized} (LLaMA~8B for cheap roles, 70B where critical), and \textit{homogeneous\_google} (all roles Gemini Flash-Lite).
\paragraph{Local open-weight presets.}
A second family of presets runs the entire pipeline on small open-weight models via \texttt{local\_hf}, so that the contribution of the multi-agent scaffold can be measured independently of cloud-scale model capacity:
\begin{itemize}[leftmargin=*,itemsep=1pt]
    \item \textit{tiny\_math\_homogeneous}: Qwen2.5-Math-1.5B-Instruct, small enough for a single entry-level GPU.
    \item \textit{qwen\_math\_7b\_local} / \textit{deepseek\_7b\_local}: Qwen2.5-Math-7B and DeepSeek-R1-Distill-7B in 4-bit NF4 quantization ($\sim$4\,GB VRAM), fitting a single 16\,GB GPU.
    \item \textit{qwen\_math\_7b\_fp16} / \textit{qwen\_7b\_instruct\_fp16}: full-precision 7B ($\sim$14\,GB), sharded across multiple GPUs via \texttt{device\_map="auto"}.
    \item \textit{qwen\_math7b\_mixed} (v12.3, extended in v13.0): the first \emph{heterogeneous} local preset, splitting roles by what they are graded on. \textbf{Qwen2.5-7B-Instruct} serves every role whose output must be \emph{parsed} (Mathematician: JSON blueprints; Hypothesis Generator: alternative blueprints; Judge: the constrained selection tag), while \textbf{Qwen2.5-Math-7B} keeps the roles graded purely on answer quality (Baseline, Programmer). Client deduplication keeps this at exactly two resident 4-bit models, and multi-GPU loads pass an explicit free-memory-aware \texttt{max\_memory} map (a plain \texttt{device\_map="auto"} second load OOM'd on a T4$\times$2 by placing weights on a GPU whose free memory did not survive materialization).
\end{itemize}
For 4-bit presets, weights are materialized as NF4 via BitsAndBytes; for full-precision presets, \texttt{bfloat16} is used on GPU (not \texttt{float16}, which overflows on Qwen2.5 attention logits) with per-device memory caps reserving headroom for the KV cache.
Client deduplication ensures that roles sharing the same (provider, model) pair share a single connection or a single resident model, avoiding redundant authentication and---critically for \texttt{local\_hf}---redundant GPU memory.
Our originally reported experiments (\Cref{sec:results}) use \textit{homogeneous\_groq} with Qwen3-32B; the local open-weight presets are the subject of the evaluation track described in \Cref{sec:experiments}.

\subsection{Component Ablation Configuration}
\label{sec:ablation}
To attribute accuracy and cost to individual components rather than to the pipeline as a whole, the \texttt{QualityAwarePipeline} exposes two Boolean switches, \texttt{enable\_siv} and \texttt{enable\_sht}, threaded through to the solver without duplicating the pipeline.
With \texttt{enable\_siv = False} (the \textbf{MAS-NoSIV} variant), the Symbolic Inverse Verifier never runs; the confidence gate still operates, but loses its highest-priority criterion (the SIV execution audit) and falls back to baseline-vs-MAS disagreement and the rule-based signals.
With \texttt{enable\_sht = False} (the \textbf{MAS-NoSHT} variant), the Critic and Judge stages are disabled and the pipeline returns the Engineer's first verified answer directly.
Because both variants share a single code path with the full system, any accuracy or API-cost difference is attributable to the toggled component alone.
The confidence-gate ordering invariant of \Cref{sec:confidence_gate} is preserved in all configurations.

\subsection{Distractor Hardening}
\label{sec:hardener}
When distractor hardening is enabled, 1--3 sentences are appended to each problem statement.
Each sentence introduces a random numeric value, person name, and item, explicitly flagged as irrelevant (e.g., \emph{``Unrelated note: Alex counted 42 stickers yesterday, but that does not affect the question.''}).
The distractor values are drawn from uniform distributions ($n_1 \in [7, 99]$, $n_2 \in [10, 250]$, $n_3 \in [2, 60]$), and names and items are sampled from fixed pools.
The Mathematician's \texttt{distractor\_check} field explicitly identifies these values, and the \texttt{givens} dictionary is supposed to exclude them.
SIV provides an additional safeguard: if a distractor value was inadvertently included in \texttt{givens}, it would appear in Layer~2's \texttt{unused\_givens} list (since the equations do not actually use it to produce the answer), flagging it in the Critic's fault localization report.
All Experiment 1 evaluations use distractor hardening.

\subsection{Implementation Robustness}
\label{sec:robustness}
Several engineering decisions are critical for reliable operation under free-tier API constraints.
\paragraph{Rate limiting.}
Independent per-provider rate limiters operate at the client level: 12 RPM for Groq (constrained by the $\sim$6K tokens/min TPM limit for 32B models), 15 RPM for Google, 10 RPM for Hugging Face, and 20 RPM for Together.
Each limiter enforces its inter-call delay using a thread-safe lock, allowing concurrent requests from multiple agents to be serialized safely.
The \texttt{local\_hf} backend is exempt: in-process inference contends only for the GPU, so it runs with an effectively unlimited limiter.
An additional inter-problem cooldown of 3 seconds (with SHT enabled) or 2 seconds (without) prevents token bursts across problems on rate-limited providers.
\paragraph{Local inference and GPU memory management.}
For the \texttt{local\_hf} backend, the model and tokenizer are lazily loaded on first use and cached on the client instance, so that roles sharing a model never hold two resident copies.
On load failure, VRAM is purged (\texttt{empty\_cache} followed by \texttt{synchronize}) before any retry, preventing fragment accumulation across attempts.
On Kaggle, the experiment harness explicitly frees each resident model (moving it to CPU, deleting it, and clearing the CUDA cache) between systems---e.g., before switching from the baseline model to a MAS variant---so that two 7B models are never simultaneously resident on a single 16\,GB GPU.
\paragraph{Token budget management.}
A daily token budget of 100,000 tokens (Groq free tier) is tracked in real time.
The \emph{estimation formula} is:
\begin{equation*}
\hat{T} = \left\lfloor \frac{|\text{input\_chars}|}{4} \right\rfloor + \lfloor 0.35 \times \text{max\_tokens} \rfloor
\end{equation*}
This realistic estimate (models rarely consume their full \texttt{max\_tokens} allocation) prevents the premature budget exhaustion that would occur with pessimistic worst-case budgeting.
Actual token usage is recorded from the API response's \texttt{usage.total\_tokens} field when available.
If the remaining budget falls below a per-problem threshold (9,000 tokens with SHT, 4,500 without), processing stops gracefully.
\paragraph{Retry and backoff policy.}
Each LLM call attempts up to 4 times (reduced from 6 in v9.0 to avoid cascading backoffs).
Authentication errors (HTTP 401, 403) are non-retryable and return immediately with a prefixed error code.
Rate limit errors (HTTP 429) extract the wait duration from Groq's error format (\texttt{"try again in Xm Y.Zs"}) and sleep for the exact requested duration plus a 5-second buffer.
If the extracted wait exceeds 600 seconds, the problem is classified as a daily-limit hit and processing stops.
Generic failures use exponential backoff with jitter: $\min(120,\ 2^{\text{attempt}} \times 5 + \mathcal{U}(0, 5))$ seconds.
\paragraph{Response caching.}
All LLM calls are optionally cached using an MD5 hash of the (provider, model, messages, temperature) tuple as key.
The cache is persisted to disk as a pickle file (\texttt{call\_cache\_v6.pkl}) and reloaded at startup, enabling deterministic re-runs of experiments without additional API costs.
\paragraph{Consecutive failure detection.}
During a pipeline run, if five consecutive problems both return ``unknown'' for baseline and MAS answers, execution aborts with a diagnostic message, preventing silent failure accumulation when an API key expires or service goes offline.

\section{Experimental Setup}
\label{sec:experiments}
% ============================================================
\subsection{Benchmarks}
We evaluate on five mathematical reasoning benchmarks:
\begin{itemize}[leftmargin=*,itemsep=3pt]
    \item \textbf{GSM8K} (test split) \citep{cobbe2021gsm8k}: 1,319 grade-school math problems requiring 2--8 reasoning steps.
    \item \textbf{GSM-Hard} \citep{gao2023pal}: GSM8K problems with numbers replaced by larger values; correct answers can be in the millions, testing numerical robustness.
    \item \textbf{GSM-Plus} \citep{li2024gsmplus}: Systematic perturbations of GSM8K covering eight types: digit expansion, distraction insertion, reversing operations, adding operations, numerical substitution, and others.
    \item \textbf{GSM-Symbolic (P2)} \citep{shi2023gsmsymbolic}: The hardest complexity level, combining symbolic value variations with additional problem clauses.
    \item \textbf{SVAMP} \citep{patel2021svamp}: Structurally varied arithmetic problems from diverse sources, testing cross-domain generalization.
\end{itemize}
\subsection{Baselines and System Variants}
\label{sec:variants}
We compare MAS-SHT against four single-model baselines and two ablations of the framework itself.
The baselines are: \textbf{B1 (Direct)}, a zero-shot answer with no reasoning; \textbf{B2 (CoT)}, chain-of-thought prompting \citep{wei2022chain}; \textbf{B-PAL}, program-aided reasoning \citep{gao2023pal}; and \textbf{B-PoT}, program-of-thought reasoning \citep{chen2023program}.
The ablations are \textbf{MAS-NoSIV} (\texttt{enable\_siv = False}) and \textbf{MAS-NoSHT} (\texttt{enable\_sht = False}), instantiated via the switches of \Cref{sec:ablation}.
All variants in a given experiment use the same underlying model, so that differences isolate the reasoning scaffold rather than model capacity.
\subsection{Language Models and Infrastructure}
\paragraph{Experiment 1 (Hard Benchmarks, cloud).}
All five benchmarks are sampled with distractor hardening enabled.
All agent roles use \textbf{Qwen3-32B} via the Groq inference API (homogeneous preset).
Groq provides low-latency access under a free-tier constraint of approximately 100,000 tokens/day at 12 RPM.
\paragraph{Experiment 2 (Standard GSM8K, cloud).}
A second run on 10 standard GSM8K problems (no distractor hardening) uses the SambaNova inference API, verifying that the framework generalizes across inference providers.
\paragraph{Experiment 3 (Local Open-Weight Models).}
A third evaluation track---enabled by the v11 blueprint-recovery mechanisms (\Cref{sec:blueprint_recovery}) and the \texttt{local\_hf} backend (\Cref{sec:heterogeneous})---runs the entire pipeline on small open-weight models at zero API cost, hosted in-process on Kaggle T4 GPUs.
It is sampled from the tractable end of the benchmark suite (GSM8K, GSM-Hard, SVAMP), where a 7B model produces blueprints frequently enough for SIV to have meaningful coverage---in contrast to competition-level sets (MATH-500, AIME), on which a 7B model exhibits a floor effect that masks any component-level delta.
The track proceeds in two phases.
\emph{Phase~A (homogeneous)}: all agent roles use a single Qwen2.5-Math-7B-Instruct (4-bit NF4) on a stratified $n{=}150$ sample drawn 50/50/50 from the three benchmarks (seed 42); this phase comprises the pilot and the v12.0/v12.1 validation runs (\Cref{sec:pilot_diagnosis,sec:v12_validation}).
\emph{Phase~B (coverage-oriented, v12.2 onward)}: the draw is reweighted to 75 GSM-Hard / 50 GSM8K / 25 SVAMP---GSM-Hard yields roughly 2.6$\times$ more genuine multi-given blueprints than SVAMP (26\% vs.\ 10\%), so the reweighting buys SIV coverage at zero GPU cost---and the roles are split across two models via the \textit{qwen\_math7b\_mixed} preset (\Cref{sec:heterogeneous}).
The reweighted draw is a \emph{different} 150-problem set than Phase~A's, so all systems (baselines included) are re-run on it, and the draw order is shuffled under the same seed so that a truncated GPU session leaves a stratified prefix rather than an all-GSM-Hard one.
In both phases constrained decoding is not engaged (the \texttt{lm-format-enforcer} acceptor is incompatible with the Kaggle \texttt{transformers} build, \Cref{sec:blueprint_recovery}); blueprint validity instead rests on the extraction cascade and the post-generation CoT recovery, plus (Phase~B) the instruction-tuned Mathematician following the JSON schema directly.
This is the designated track for the dedicated SIV evaluation, as it includes the MAS-NoSIV ablation (\Cref{sec:variants}) on a model that the pipeline can actually drive end-to-end.
\paragraph{Note on SIV evaluation.}
The experiments of \Cref{sec:results} were conducted under v9.1 of the pipeline, prior to the integration of SIV in v10.0; SIV metrics therefore appear as \texttt{null} in those logs.
The two-layer impact of SIV---the execution-audit catch rate, the rate at which SIV correctly skips SHT on execution-consistent problems, the execution-layer-vs-translation-layer error decomposition, and the accuracy and cost delta against the MAS-NoSIV ablation---is the explicit object of Experiment~3.
As of v13.0, Phase~B has closed the coverage precondition (SIV audits 72.7\% of problems, up from $\sim$37\%) and characterized the verification signal in the field (\Cref{sec:v13}); the MAS-NoSIV ablation on the Phase~B problem set is the remaining measurement for a causal, rather than correlational, SIV claim.
A dedicated analysis module (\Cref{app:siv_eval}) computes these tables directly from the per-problem run logs.
\subsection{Temperature and Token Settings}
Role-specific temperatures: $\tau=0.0$ (Mathematician, Judge), $\tau=0.05$ (Programmer), $\tau=0.1$ (Baseline), $\tau=0.3$ (Critic).
Token budgets differ by pipeline version. Experiments~1--2 used the v9.1 reduced settings: Baseline and Judge 500 tokens, Mathematician 600 tokens, Programmer 1000 tokens, Critic 900 tokens. Experiment~3 uses the v11.2 settings, which raise the Baseline to 1024 and the Mathematician to 1536 tokens (with the simplified blueprint retry at 1000 and the CoT-extraction call at 800), while leaving the Programmer (1000), Critic (900), and Judge (500) unchanged. The Mathematician increase directly targets the mid-object truncation diagnosed in \Cref{sec:discussion}.
\subsection{Evaluation Metrics}
\paragraph{Accuracy.}
A prediction is correct if the extracted numeric answer matches the gold answer within $\epsilon=10^{-3}$.
Gold answers use the \texttt{\#\#\#\#} delimiter format standard in GSM8K; SVAMP and GSM-Plus provide direct numeric fields.
\paragraph{SHT-specific metrics.}
Trigger rate, rescue count (baseline wrong $\to$ MAS correct), damage count (baseline correct $\to$ MAS wrong), net benefit, and triage method distribution.
\paragraph{Solver path metrics.}
Fraction of problems resolved by Programmer (optimized), empty blueprint, Programmer (failed after repairs), and SymPy fallback.

\section{Discussion}
\label{sec:discussion}
% ============================================================
\subsection{Blueprint Construction as the Sole Bottleneck}
The most important empirical finding of this work is precise: MAS-SHT achieves \emph{100\% accuracy when the Programmer generates valid executable code}.
All 21 wrong answers in Experiment 1 originate from problems where the Mathematician either failed to produce parseable JSON (14 cases) or produced an empty blueprint despite the retry (3 additional cases).
This finding sharply delineates the research agenda: improving the downstream pipeline (verification, SHT, Judge) yields diminishing returns; improving blueprint construction yields proportional accuracy gains.
Empty blueprints arise primarily in two scenarios:
\textit{(i)} complex multi-clause problems (GSM-Symbolic P2 contributes 5 of the 14 empty blueprints) where the model exhausts its (v9.1) 600-token budget writing reasoning prose before emitting JSON; and
\textit{(ii)} problems requiring non-trivial mathematical structuring (percentages, proportions, inverse rates) where the model fails to identify a clean Python-expressible equation chain.
The token budget cap is thus an active constraint, and v11.2 acts on it directly: the Mathematician budget is raised from 600 to 1536 tokens (\Cref{sec:experiments}), explicitly to let the model finish a complete JSON object rather than truncating mid-blueprint after exhausting the budget on reasoning prose---attacking scenario~\textit{(i)} at its root.
The remaining v11 mechanisms of \Cref{sec:blueprint_recovery} address the residual cases: constrained decoding would make malformed output unrepresentable (available but not engaged in v11.2, \Cref{sec:blueprint_recovery}), while two-step CoT extraction removes much of scenario~\textit{(ii)} by recovering structure from a derivation the model \emph{can} produce even when it cannot emit clean JSON \emph{ex nihilo}. Quantifying how far the raised budget and CoT extraction close the 37.8\% empty-blueprint gap on small open-weight models is the central question of Experiment~3.
\subsection{Correlated Errors and the Critic Design}
A central architectural decision in v9.0 was replacing the ``5 strategy archetypes'' parallel generation approach with critic-based peer review.
Under the original design, the same model was instructed to generate two alternative blueprints from different mathematical archetypes (Arithmetic-Sequential, Algebraic-Equational, Unit-Rate, Working-Backwards, Partitioning).
In practice, however, correlated errors dominated: the same misidentified variable or incorrect operation appeared in all alternatives, because the model's systematic misconception about the problem was not affected by the archetype constraint.
Majority voting over correlated candidates is provably no better than selecting a single random candidate.
The critic design introduces a qualitatively different cognitive demand: the model must first articulate \emph{what is wrong} before generating a correction.
This metacognitive framing partially breaks correlation because the model must commit to a specific failure hypothesis---and different failure hypotheses lead to structurally different corrections.
The interpretable \texttt{strategy\_name} values observed in our data (e.g., \texttt{correction\_of\_missing\_steps} in the one majority-resolution case) confirm that the Critic does identify distinct, actionable errors rather than merely rephrasing the primary approach.
\subsection{Symbolic Inverse Verification: Two-Layer Design and Scope}

SIV introduces a two-layer deterministic audit that targets the \emph{execution layer} of the Architect--Engineer pipeline.

\paragraph{Layer~1 (Execution Audit) as the primary signal.}
The most direct contribution of Layer~1 is detecting when the Programmer's computed answer deviates from what the blueprint equations actually evaluate to.
This is a necessary precondition for any meaningful inverse reasoning: if the Programmer's answer does not match the forward evaluation of the blueprint, the execution is incorrect regardless of whether the blueprint itself is correct.
Layer~1 is the first check that runs and sets the interpretation frame for Layer~2.

\paragraph{Layer~2 as the Critic enabler---corrected scope.}
Our original design intended Layer~2 to identify precisely which declared given variable is inconsistent with a deviating answer.
The controlled fault-injection evaluation of \Cref{sec:siv_fault_injection} shows this is not what the mechanism delivers once 2 or more givens are used: holding every other given fixed at its declared value and inverting for one at a time generically flags \emph{every} used given together (mean precision $1/n_{\text{used}}$, exact isolation 0\%), because the blueprint's equations collapse to a single scalar constraint over all used variables---perturbing any one of them requires every other one's one-at-a-time reconstruction to disagree too, not just the true culprit.
What the same evaluation shows Layer~2 \emph{does} deliver reliably (100\% in all 12 test blueprints) is the separation of declared-but-unused (distractor) givens from used ones, plus a guarantee that the true fault is never absent from the reported set (100\% recall across 37 corruptions).
Relative to FOBAR \citep{jiang2024fobar}, which produces a binary pass/fail verdict, SIV's actual novel contribution is therefore a deterministic, zero-cost, structured diagnostic---an implicated-variable set with validated distractor exclusion---not per-variable point localization.
This still narrows the Critic's first alternative from speculative re-derivation toward the load-bearing variables, short of pinpointing a unique fault.

\paragraph{The tautology property and why Layer~2 is honest about it.}
When Layer~1 passes (\texttt{execution\_audit\_passed = True}), the Programmer's answer is exactly what the blueprint equations compute, which means Layer~2's inverse reconstructions are \emph{guaranteed} to pass---they are algebraic rearrangements of the same expression.
This is not a failure of SIV; it is an inherent property of any math$\to$math verifier.
We address this by: (i)~making the execution audit the explicit primary signal; (ii)~capping SIV confidence below 1.0 even on full reconstruction ($\leq 0.97$) to reflect that the NL$\to$math layer is untested; and (iii)~documenting the limitation in \texttt{verifies\_translation = False}.

\paragraph{Explicit scope: NL$\to$math errors are outside SIV's detection range.}
SIV cannot detect a blueprint that correctly executes the wrong equations---i.e., a blueprint that models the problem incorrectly but is internally consistent.
This is the translation layer, and it is FOBAR's comparative advantage.
The correct architectural response is \emph{composition}: use SIV for execution-layer audit and fault localization, and use a separate NL-layer verifier (LLM-based or human) for translation correctness.
Future work should evaluate whether adding a lightweight FOBAR-style check as an additional confidence gate criterion improves accuracy beyond either method alone.

\paragraph{Additional scope flags.}
Two further limitations are explicitly encoded in the implementation.
(i)~\emph{Non-invertible chains}: equations with \texttt{floor}, \texttt{ceiling}, absolute value, or conditional branches may not yield closed-form SymPy solutions; SIV abstains for those variables.
(ii)~\emph{Empty blueprints}: when the Mathematician fails (37.8\% of Experiment~1), SIV cannot run at all, which is precisely the regime where verification is most needed.

\subsection{The Baseline as an Active Triage Participant}
A subtle but important design choice is registering the zero-shot baseline answer as a triage candidate with a fixed confidence of 0.5.
This choice has two effects.
First, on problems where both the primary and the Critic's alternatives fail code execution, the baseline answer alone can achieve a ``unanimous'' triage outcome (two failed candidates plus baseline), which the Judge then confirms or overrides.
This explains the high Judge rate (48.6\%): the Judge is not called because candidates \emph{disagree}, but because only the baseline is a ``valid'' candidate in the triage sense.
Second, on standard benchmarks where the baseline is highly reliable, its participation in triage provides additional confirmation of correct answers, potentially reducing false SHT triggers.
\subsection{The Role of the SymPy Fallback}
Although SymPy was not invoked as the final solver in any of the 37 Experiment 1 problems, it plays a structural role that is difficult to quantify from these results alone: as a post-programmer-failure fallback (confidence 0.8), it provides a backstop against code generation failures when the blueprint equations are correct.
In the $n{=}150$ pilot this path resolved 16 problems at 68.8\% accuracy---below the Programmer path but far better than returning ``unknown''.
The \emph{second} historical invocation point---replacing the Programmer's answer when rule-based verification failed---was removed in v12 after the pilot measured it at 33\% accuracy against the 50\% of the answers it overwrote (\Cref{sec:pilot_diagnosis}); the blueprint's CAS evaluation now competes in arbitration instead of overwriting the primary.

\subsection{Pilot Diagnosis at $n{=}150$: The Selection Layer, Not the Solvers, Was the Bottleneck}
\label{sec:pilot_diagnosis}
Before the v12 redesign we ran the full system and three baselines on an identical stratified sample of 150 problems (GSM8K, GSM-Hard, SVAMP) with Qwen2.5-Math-7B-Instruct as the sole model for every role (\texttt{local\_hf} backend, Kaggle GPU, seed 42).
The headline numbers were sobering: direct answering 60.0\%, zero-shot CoT 80.7\%, single-call PAL 88.0\%, and the full MAS-SHT pipeline \textbf{74.0\%}---the multi-agent system was \emph{losing} 14 points to a single-call baseline it contains as a component.
Path-level decomposition, however, localized the damage precisely:
\begin{itemize}[leftmargin=*,itemsep=2pt]
    \item \textbf{confident\_skip} (101/150 problems): 96.0\% accurate---when the gate accepted the primary answer, the system was essentially as good as agreement-filtered PAL;
    \item \textbf{unanimous} triage (9): 88.9\%;
    \item \textbf{judge} triage (40): \textbf{15.0\%}, on problems where the internal baseline answer it was free to select scored 42.5\%. The judge path converted 16 correct answers into wrong ones while fixing only 6.
\end{itemize}
Five concrete mechanisms, each independently verifiable in the run logs, produced this failure:
\begin{enumerate}[leftmargin=*,itemsep=2pt]
    \item \textbf{Free-form judging with text scraping.} The judge emitted free text; when its \texttt{SELECTED\_ANSWER} tag failed to parse, the pipeline scraped the \emph{last number in the rationale} as the final answer---returning candidate indexes and confidence values (predicted answers of 1, 2, 3, 4, 5, 8 against three-to-seven-digit golds).
    \item \textbf{A falsy-zero guard disabled the SIV anchor exactly when SIV was most certain.} The v11.4 anchor required \texttt{(execution\_rel\_error or 1.0) < 1e-3}; a \emph{perfect} audit (\texttt{rel\_error = 0.0}) is falsy in Python, so the guard read 1.0 and never fired. On \texttt{gsm-hard\_1125} (rel.\ error $5.5\times10^{-4}$) the anchor fired and fixed the answer; on \texttt{gsm-hard\_542} the SIV-verified blueprint answer \emph{equaled the gold} ($-4416673$) with rel.\ error exactly 0.0, the anchor was skipped, and the judge output ``3''.
    \item \textbf{Blueprint coupling.} The Programmer transcribed the Architect's equations verbatim, so a mistranslated blueprint became a faithfully wrong program (PAL, free of this coupling, scored 88.0\% vs 74.0\%).
    \item \textbf{Verification-triggered answer replacement.} SymPy re-solves of the blueprint overwrote executed answers at 33\% accuracy against the 50\% they replaced.
    \item \textbf{Unconditional negative-answer alarm.} Every negative primary triggered SHT even when the baseline agreed; on the six negative-gold GSM-Hard problems the system scored 17\% against PAL's 83\%.
\end{enumerate}
Each mechanism maps one-to-one onto a v12 change: constrained index-only judging with a no-scrape guarantee, an explicit \texttt{is not None} anchor guard, the PAL-style Programmer, advisory-only verification, and the agreed-negative exemption---plus the blueprint-evaluation vote and evidence ranking of \Cref{sec:evidence_arbitration} that remove most judge invocations altogether.
Two aspects of this diagnosis deserve emphasis.
First, the pilot \emph{validates} the framework's core premises even while indicting its selection layer: execution-based solving, cross-derivation agreement gating, and SIV's audit signal were all individually healthy (agreement-gated answers: 96\%; SIV-verified answers: 73.3\% vs 53.5\% for unverified).
Second, it supplies the honest motivation for verification-weighted arbitration: in a homogeneous small-model deployment, \emph{the same 7B model that solves problems well judges them poorly}, so authority must rest with deterministic, verifiable evidence, and LLM judgment must be constrained to choices that evidence cannot separate.

\subsection{v12.0 Validation Run: +8.7 Points, and a Second Selection-Layer Bug Found by Analyzing It}
\label{sec:v12_validation}
We re-ran the identical 150-problem set (same model, same seed) under the v12.0 redesign.
Overall accuracy rose to \textbf{82.7\%} (124/150), up from 74.0\% under the pre-v12 selection layer on the same problems---an \textbf{+8.7 percentage point} gain attributable entirely to the selection-layer fixes, since the upstream solvers (Architect, Programmer, SIV) are otherwise unchanged.
Path-level accuracy confirms the diagnosis was correct: \texttt{confident\_skip} rose to 96.9\% (96/150) and \texttt{unanimous} to 100\% (18/150), both consistent with the pilot; SIV-verified answers were now \textbf{100\% correct (12/12)} against 65.9\% for unverified answers---the first clean confirmation that SIV's signal, once acted upon correctly, is trustworthy.
Two triage paths remained below the confident-skip level: \texttt{majority} (40.0\%, 10 problems) and \texttt{evidence} (34.6\%, 26 problems).

Decomposing the \texttt{evidence} and \texttt{majority} rows by candidate count isolated a second, more specific defect.
Of the 21 problems that reached the single most common no-majority configuration---a lone Programmer answer against a lone zero-shot baseline, with no SIV signal and no surviving Critic alternative---the v12.0 arbitration rule resolved \emph{every single one} in favor of the primary.
This was not evidence-driven: the \texttt{executed} scoring component in \Cref{sec:evidence_arbitration} treats ``a group contains an executed-code answer'' as evidence, but in this exact configuration the primary always has code and the baseline never does, so the component degenerates into an unconditional preference for the primary regardless of correctness.
The data show this plainly: of the 21 tied problems, the primary was correct on 7 and the baseline was correct on a \emph{disjoint} other 7---a coin flip, not a signal---yet the deterministic rule always chose the primary, recovering its own 7 while converting all 7 baseline-correct cases into regressions (silently damaging already-correct answers, the outcome class this framework is designed to avoid).
\paragraph{Fix (v12.1).} \texttt{\_select\_by\_evidence} now auto-resolves a group ranking only when the winning group carries genuine corroboration: either multiple independent derivations agree (\texttt{votes} $\geq 2$, reachable here only through a size-tied 2-vs-2 configuration) or SIV fully verified that exact value. A field of lone, unverified singletons---whichever candidates they happen to be---is no longer decided by a structural artifact; every one of them is escalated to the constrained Judge, the mechanism designed for genuine ties.
\paragraph{Honest bound, never directly re-measured.} This fix responds to a defect discovered by analyzing the v12.0 run's own log, not to a second full execution.
We can bound its effect from the same log: on the 21 affected problems, always keeping the primary (the v12.0 behavior) scores 7/21, and an oracle that always picks whichever of the two is actually correct scores 14/21---raising the overall total from 124/150 (82.7\%) to at most 131/150 (87.3\%), i.e.\ parity with PAL, if the tie-resolution mechanism performs at oracle level; the floor is the unchanged 82.7\% if it does no better than the coin flip it replaces.
This projection was never tested in isolation: rather than re-running the identical (easier) Phase~A mix, the evaluation moved directly to the coverage-oriented Phase~B configuration (\Cref{sec:v13}), which changes the benchmark mix and the model assignment simultaneously---and whose own selection-layer findings (\Cref{sec:do_no_harm}) superseded the v12.1 rule, replacing judge escalation of uncorroborated ties with a baseline default.
The v12.1 bound therefore remains a bound; the closest available observation is that on Phase~B's GSM8K/SVAMP portion the v13.0 system measures 86.7\% (\Cref{sec:v13}), consistent with the upper half of the projected range, but on different problems and under a different preset, so it is corroborating context rather than a controlled measurement.
\subsection{Raising SIV Coverage, a Second Collapse, and v13.0 Baseline-Anchored Selection}
\label{sec:v13}
The v12 validation run left SIV's dedicated evaluation starved: only 19.3\% of problems (29/150) produced a genuine multi-given blueprint for Layer~2 to audit, and 11 of the 12 SIV-verified answers sat in the degenerate single-given regime.
Phase~B of Experiment~3 attacks this precondition with the two levers already identified in our own future-work analysis: the benchmark draw is reweighted toward GSM-Hard (75/50/25; \Cref{sec:experiments}), and the \textit{qwen\_math7b\_mixed} preset (\Cref{sec:heterogeneous}) assigns the instruction-tuned sibling to every parse-critical role.
Because the reweighted draw is a different problem set, all baselines were re-run on it: direct answering scores 48.7\%, zero-shot CoT 74.7\% (down from 60.0\% and 80.7\% on the Phase~A mix, confirming the new mix is substantially harder); PAL completed only its GSM-Hard block (62.7\%, 75 problems) before a session interruption, so its full-mix figure is pending.

\paragraph{The coverage goal was met immediately.}
On the first Phase~B run, empty blueprints fell from 62.7\% to \textbf{27.3\%} of problems and SIV audited \textbf{109/150 (72.7\%)}, up from $\sim$37\%---the single largest coverage improvement in the project's history, and exactly the regime the SIV evaluation needs.

\paragraph{End-to-end accuracy collapsed anyway.}
The same run scored \textbf{57.3\%}---17.4 points below plain CoT on the identical problems---while its \emph{own internal zero-shot baseline} was right 75.3\% of the time.
As in the pilot, the damage was localized to the selection layer, and the run's log identified three mechanisms, quantified in \Cref{sec:do_no_harm}: a pseudo-vote that let the \{primary, blueprint-eval\} pair outvote the independent baseline (baseline right 30/36 on those rows), SIV verification acting as a standalone override authority (22/22 correct with baseline agreement, 2/14 against it), and a judge-failure fallback that structurally preferred the primary (fired 55/150 because the Math-7B judge never emitted its tag before the token cap; 8/55 vs.\ the discarded baseline's 29/55).
It is worth stating plainly why the defects surfaced only now: the mixed preset and the reweighted mix together made blueprints \emph{form} at roughly twice the old rate (37.3\% $\to$ 72.7\%), so arbitration paths that had almost never executed before (majority over blueprint votes, judge fallback) suddenly carried a third of the problems---coverage did not cause the collapse, it \emph{exposed} latent selection-layer bugs that thin coverage had been hiding.

\paragraph{v13.0 measurement.}
Under the do-no-harm invariant and the audit-triggered repair loop (\Cref{sec:do_no_harm,sec:siv}), re-running the identical Phase~B set measures \textbf{72.7\% (109/150)}, a +15.4-point recovery over the collapse with no change to the underlying solvers.
The invariant's wiring is verified exactly, not just statistically: on all 51 problems that ended in \texttt{baseline\_default}, the final answer equals the internal baseline's answer verbatim (0 mismatches)---``never lose to your own zero-shot baseline for structural reasons'' now holds by construction.
Decomposition explains most of the apparent regression against Phase~A's 82.7\%: the GSM8K/SVAMP portion of the mix scores \textbf{86.7\%} ($n{=}75$; above the 82.7\% measured on the easier Phase~A mix), while GSM-Hard scores 58.7\% ($n{=}75$; above CoT's 56.0\% and below PAL's 62.7\% on the same subset)---and GSM-Hard is now 50\% of the set rather than 33\%, precisely because it was upweighted for SIV coverage.
The residual gap to CoT's full-mix 74.7\% is three problems (2.0 points); against its own internal baseline the system shows 8 losses and 4 gains through the corroborated (majority/evidence) paths, a difference that is not statistically significant (exact McNemar, $p=0.39$).
The honest reading: corroboration fired exactly as designed, and corroboration itself is simply not infallible at this sample size.

\paragraph{Repair loop: detection is not correction.}
The blueprint repair loop fired on 39/150 problems, but only 6/39 (15.4\%) of repairs subsequently produced a clean execution-audit pass.
This gap between the trigger's detection quality (80.3\% recall, zero false alarms) and the repair's fix rate is an instructive negative result: the audit reliably \emph{flags} a bad blueprint, but a second attempt by the same 7B Mathematician---even armed with SIV's localization report---usually cannot fix what it got wrong the first time.
Net accuracy effect was roughly neutral (repaired blueprints appear in 3 of the 8 losses and 3 of the 4 gains), though the repaired path enabled most of the genuine value-added cases.
For future write-ups we record the distinction explicitly: \emph{detection recall} and \emph{fix success rate} are different quantities, and measuring one licenses no assumption about the other.

\paragraph{What this arc establishes about SIV.}
Across the collapse diagnosis and the v13.0 run, SIV's role in the architecture has clarified into three validated uses and one prohibited one: (i)~a \emph{cross-validator} for the confident skip---jointly with baseline agreement it was 97.9\% accurate on the mixed run, and SIV-verified-plus-baseline-agreed answers were 22/22; (ii)~a deterministic \emph{tie-breaker} between corroborated candidate groups; (iii)~an in-loop \emph{repair trigger} with validated detection quality; and---prohibited---(iv)~a standalone override authority, because certifying blueprint-internal consistency inherits the blueprint's translation errors (2/14 against a disagreeing baseline), which is this paper's math$\to$math scope claim (\Cref{sec:siv}) measured in the field.

\subsection{The MAS-NoSIV Ablation and the Certificate--Difficulty Confound (v14)}
\label{sec:v14_routing}
The causal measurement flagged throughout this paper as outstanding has now run: MAS-NoSIV on the identical Phase~B problem set, same preset, identical per-row baseline answers.
The result is a genuine negative: \textbf{72.00\% without SIV vs.\ 72.67\% with it} (3 paired wins, 2 paired losses; exact McNemar $p \approx 1.0$).
Used as an \emph{arbitration} signal, SIV is causally neutral on this configuration.
We report this plainly and then explain it, because the explanation---not the null---is the finding.

\paragraph{Why arbitration cannot be where SIV pays.}
On the same run, the blueprint path is \emph{uniquely} right (correct where the baseline is wrong) on only 2/150 problems, so the oracle over \{baseline, blueprint\} is 76.7\% against the baseline's 75.3\%: every conceivable improvement to selection between them is capped at +1.4 points.
Removing the baseline from the pool entirely makes the ceiling starker: the technique's own four candidates (primary, CAS-evaluated blueprint, two Critic alternatives) admit an oracle of 55.33\%, with blueprint accuracy at 20.7\% the binding term---the conditional structure is sharp (blueprint correct $\Rightarrow$ Programmer correct 96.8\%; blueprint wrong $\Rightarrow$ 43.3\%), and fitting it gives $\text{primary} \approx 0.433 + 0.535 \cdot \text{blueprint}$, which requires blueprint accuracy near 64\% before the technique clears its own zero-shot baseline unaided.
No selection layer can manufacture that from 20.7\% material.

\paragraph{The certificate is confounded with problem difficulty.}
SIV's execution audit remains an excellent \emph{detector}: on the 94 genuinely audited rows of the v14.4 run, a FAILED audit implies the blueprint's answer is wrong with 98.1\% precision at 81\% recall.
The failure is on the other side of the certificate.
On the 42 audit-PASSED rows, the certified blueprint answer is 71.4\% correct---but the plain CoT baseline on those \emph{same} rows is 88.1\% correct, so overriding the baseline with the certified answer is worth $-16.7$ points (95\% bootstrap CI $[-31.0, -2.4]$).
No subgroup reverses the sign (confidence $\geq 0.90$: $-17.5$; givens matched $\geq 2$: $-16.1$).
The mechanism: a blueprint that survives a symbolic audit is disproportionately a blueprint of an \emph{easy} problem---and easy problems are exactly where the baseline is already strong.
The methodological point generalizes beyond this system: \emph{a verifier's positive predictive value must be compared against the baseline's accuracy conditioned on the certificate}, $\Pr(\text{correct} \mid \text{certified})$, not against the unconditional base rate; by the unconditional comparison (71.4\% vs.\ 33\% base rate) the certificate looks strong, and acting on that comparison is precisely what the do-no-harm invariant had been silently absorbing.

\paragraph{Verification as routing, not arbitration (v14.6).}
The same certificate that fails as an override authority succeeds as a \emph{compute allocator}: it separates the baseline's own accuracy by +26.6 points (88.1\% on certified rows vs.\ 61.5\% on uncertified; 95\% CI $[+10.3, +42.9]$), it is available before the expensive Critic stage runs, and it costs nothing.
Recoverable headroom concentrates exactly where the certificate is absent: oracle-minus-baseline is +17.3 points on uncertified rows against +4.8 on certified ones.
v14.6 therefore routes: tier~A (a free candidate corroborates the baseline) and tier~C (audit passed or absent, no corroboration) return the do-no-harm anchor without spending Critic calls; only tier~B (audit FAILED and no corroboration) pays for hypothesis testing.
On the v14.4 data this replay projects $75.33\%$ while reclaiming 63\% of wall time, with tier~B worth a projected +7.1 points on its stratum.

\paragraph{v14.8 measurement.}
With routing live, blueprint evaluation unconditional (a plumbing gate had silently excluded every SymPy-fallback row, 18.7 points of coverage), and two further deterministic repair classes, the next full run measures \textbf{75.33\% against its internal baseline's 74.67\%}---the first time in the local track the full system finishes above its own zero-shot baseline---with blueprint coverage 86.0\% (the projection said 129/150; the run produced 129/150), 3 paired wins against 2 losses, and tier~B delivering +6.9 points on its stratum against the +7.1 projected.
We do not overclaim this margin: +0.67 points on $n{=}150$ is one problem and is not statistically significant.
Its significance is structural: the coverage, routing, and repair projections made offline from stored run logs were each confirmed by the GPU run within a problem or two, which is the methodological pattern this project has converged on---\emph{measure on logged artifacts first, spend GPU hours only to confirm}.

\subsection{The Architect Misreads the Operands, Not the Problem: Deterministic Operand Grounding (v15)}
\label{sec:v15_grounding}
With arbitration retired as a lever (\Cref{sec:v14_routing}), the binding constraint is blueprint accuracy itself.
A 5-route pretest (25 problems $\times$ 5 prompt variants under greedy decoding, so all diversity is prompt-induced) was run to test blueprint ensembling---and rejected it (across variant pairs where both are wrong, 22.8\% land on the same wrong value, but the $\geq$2-agree rule nets +1 problem in 25 at $5\times$ Mathematician cost).
The pretest's stored blueprints, however, admit a far more consequential diagnosis when checked against the problem texts:
\begin{itemize}[leftmargin=*,itemsep=2pt]
    \item \textbf{35\% of extracted numeric givens appear nowhere in the problem text.}
    \item \textbf{68\% of those sit exactly one digit away from a number that does}: ``Katelyn saw 50 fairies \ldots 30 fairies flew away'' is extracted as 55 and 31; ``Kim raises \$320 more than Alexandra, who raises \$430'' becomes 321 and 431; ``569 girls and 236 boys'' becomes 69 and 36.
    \item Across variant pairs where one is right and the other wrong, \textbf{38\% share the identical equation structure} and differ only in an operand.
\end{itemize}
The Architect, at this model scale, is predominantly not failing to \emph{reason} about the problem; it is failing to \emph{copy} it.
This reframes the NL$\to$math translation layer that SIV's scope statement (\Cref{sec:siv}) declares out of reach: the dominant translation defect is not semantic modelling error but operand transcription---and transcription, unlike semantics, is mechanically checkable against the problem text.

\paragraph{Deterministic repair of the transcription layer (v15.0--v15.2).}
\texttt{repair\_blueprint} now receives the problem statement and applies, in order: (i)~\emph{operand grounding}---any numeric given absent from the text is rewritten \emph{only} when exactly one text number is a single digit-edit away, or exactly one shares its digit suffix (a dropped leading digit), or---for integers $\geq 10^4$, where gsm-hard's perturbed operands live and text numbers of that magnitude are rare---exactly one $\geq$5-digit text number is within two digit-edits; any ambiguity abstains; (ii)~\emph{expression-valued givens}---a given declared as a formula string (\texttt{"fairies\_from\_east": "initial\_fairies / 2"}, \texttt{"1/4"}) is evaluated by a restricted AST walk over arithmetic operators and names resolving to other numeric givens, after grounding, so the expression reads corrected operands and its result is never itself snapped; and (iii)~\emph{accessor respelling} (\texttt{givvens['x']} $\to$ \texttt{givens['x']}).
Values requiring semantics (\texttt{"5 pm"}, names resolving nowhere) are refused and continue to the LLM repair path.
Every rule is deterministic, zero-LLM, logged per fix, and guarded by refusal tests.

\paragraph{Measured on the stored pretest blueprints (125 blueprints, zero GPU).}
\Cref{tab:v15_grounding} shows per-route blueprint accuracy raw and under the full v15.2 repair.
No previously-correct blueprint is broken by any rule on any route.
The repair composes with the prompt route rather than duplicating it: the \emph{inventory} route (``list every number in the text with what it counts, then decide relevance'') is best both raw (44\% vs.\ 28\% for the production prompt) and repaired (60\% vs.\ 48\%), and its repaired correct-set nearly contains the production route's (4 problems only inventory gets; 1 only production gets).
v15.2 accordingly promotes the inventory route to the production Mathematician prompt (env-revertible for ablation).
Through the fitted $\text{primary} \approx 0.433 + 0.535 \cdot \text{blueprint}$, blueprint accuracy of 60\% projects the Programmer path alone to $\sim$75\%---at the zero-shot baseline before any selection-layer gain, for the first time.
We flag the honest caveats explicitly: the route comparison rests on $n{=}25$ problems (the repair measurements rest on all 125 blueprints), the projection is a fitted conditional rather than a measurement, and the end-to-end GPU run of v15.2 is pending.

\paragraph{Benchmark label noise bounds the remaining headroom.}
Auditing the problems no repaired route solves also surfaced ground-truth defects: GSM8K test item 1309's official solution is internally inconsistent (it totals $750+430+400+700$, substituting Maryam's \emph{increment} for Sarah's raised amount; the problem as stated yields 2180, the label says 2280), and several GSM-Hard items carry automatically-perturbed gold answers that are physically impossible for their own question (e.g.\ a negative weekly fuel cost).

\subsection{Vote Independence Requires Grounded Premises (v15.3)}
\label{sec:v153_grounded_votes}
The v15.2 GPU run delivers the projected component gains and a top-line lesson about where they went.
On the fixed 150-problem set, blueprint accuracy nearly doubles (20.7\% $\to$ 40.67\% of all problems; 49.2\% of the 124 covered), the program-aided primary rises 50.0\% $\to$ 55.33\%, and the oracle over the candidate pool reaches \textbf{84.67\%}---ten points above the baseline.
The shipped answer, however, measures \textbf{74.00\% against 74.67\%}: arbitration returned the component gains, and one problem more.

\paragraph{The gap is one mechanism, localized exactly.}
Cross-referencing per-candidate correctness against triage outcomes shows the run's \emph{entire} paired win/loss set against the baseline---2 wins, 3 losses, no remainder---is the 5 rows where the Critic's first alternative numerically agreed with the primary and the pair's two ``honest'' votes overrode the baseline.
This is the exemption v15.1 introduced deliberately: alternatives are repaired against the problem text, so an alternative that agrees with a correct lone primary was allowed to corroborate it (on the v14.8 run, 13 of 16 correct-but-lone primaries had been suppressed back to the baseline).
The exemption is symmetric, and that is the defect: the Critic is seeded with the \emph{same} blueprint and the \emph{same} SIV error report as the primary, so when the Architect's original misread survives repair, the alternative reproduces it, and the agreement is one mistake observed twice.
Conditional accuracy of the alternatives on this run: 4/10 and 2/10---not material fit to outvote an independent baseline unconditionally.

\paragraph{A free discriminator separates the wins from the losses perfectly.}
Both wins ride on blueprints whose every numeric given appears verbatim in the problem text; all three losses do not (one blueprint carries a non-numeric given \texttt{"t"}, one an operand found nowhere in the text, one a computed total stored as a given).
v15.3 therefore makes premise quality a precondition for corroboration: when the primary blueprint fails \texttt{operands\_grounded}---some given is neither a text number, nor a structural constant, nor a value the expression pass itself derived---the whole derivation family \{primary, blueprint-eval, alternatives\} present in one answer group collapses to a \emph{single} honest vote, and the do-no-harm invariant returns the baseline.
Grounded blueprints keep the v15.1 behaviour unchanged, and a group containing the baseline is unaffected.
Replayed over every alternative-bearing row of the run, the rule keeps both wins, returns all three losses to the baseline, and flips nothing else.

\paragraph{Measured, and an unusually clean controlled comparison.}
Re-running the full pipeline under v15.3 measures \textbf{76.00\% (114/150) against the same 74.67\% baseline}, with \textbf{2 wins and zero losses}---the first configuration in this track to finish above its own zero-shot baseline without surrendering a single problem to it.
Because the local backend decodes greedily, the re-run reproduced every candidate byte for byte: \texttt{cand\_primary}, \texttt{cand\_blueprint\_eval}, \texttt{cand\_alt\_1}, \texttt{cand\_alt\_2} and the baseline answer are identical on all 150 rows across the two runs.
The comparison therefore isolates the selection rule exactly---same problems, same models, same candidates, one changed predicate---and exactly four rows move: the three predicted repairs plus one wrong-to-wrong row, reproducing the offline replay to the row.
This also validates the working method the project converged on: compute the effect from stored artifacts first, and spend GPU hours only to confirm it.

\paragraph{Epistemic status, stated plainly.}
Three caveats bound this result, and we prefer to state them than to let the headline carry more weight than it can.
First, \emph{it is not statistically significant}: 2 wins against 0 losses gives an exact McNemar $p = 0.50$, and even the candidate-matched v15.2-versus-v15.3 comparison (3 repaired, 0 broken) gives $p = 0.25$.
Second, and more consequentially, \emph{the rule was derived from this problem set and evaluated on it}. The discriminator was found by inspecting the five rows that decided the v15.2 run, and because the candidates are deterministic, the confirming run re-executes the selection layer over those same candidates rather than testing it out of sample. What the run establishes is that the implementation behaves exactly as the analysis predicted; what it cannot establish is the rule's transfer. A fresh draw under a different seed is therefore the single most valuable remaining measurement, and we would require it before treating $+1.33$ points as the rule's expected effect.
Third, what carries the rule beyond the fit is its form rather than its margin: it introduces no tuned threshold, and it is \emph{restriction-only}---it removes override authority and never grants it, so its worst case is the do-no-harm floor rather than a new class of damage.
The design principle it adds to the arc of \Cref{sec:do_no_harm,sec:v14_routing}: \emph{agreement between derivations that share a premise is admissible corroboration only when the shared premise is externally verified}---here, verified against the problem text at zero cost.
\paragraph{Where the remaining headroom sits, and why we did not take it.}
The oracle over the candidate pool is 86.00\%, and 15 problems have a correct candidate the baseline misses; the shipped system captures 2, leaving 8.67 points unrealised.
Eight of the thirteen missed problems share one signature: compute-routing tier~C, execution audit passed, and the primary agreeing with its own CAS-evaluated blueprint against the baseline---the certificate-difficulty zone of \Cref{sec:v14_routing}, which the do-no-harm anchor currently resolves in the baseline's favour without exception.
Applying the same grounding predicate there is measurable and points the same way: on that zone's 18 rows the grounded subset ($n{=}12$) has the primary right 5 times against the baseline's 3, while the ungrounded subset ($n{=}6$) has the primary right \emph{zero} times against the baseline's 4.
We report this as a diagnosis rather than shipping it. Five-versus-three at $n{=}12$ is a two-problem margin on the very run that would justify it, and adopting it would convert a restriction-only invariant into an override rule on exactly the evidence class this paper has twice measured to be confounded with problem difficulty.
It is the natural next hypothesis, and it needs a fresh problem set to test rather than a re-fit of this one.

\subsection{API Cost Analysis}
The observed average API call count per problem in Experiment 1:
\begin{equation*}
\bar{c} = 0.054 \times 3 + 0.459 \times 4 + 0.459 \times 5 + 0.027 \times 6 = 4.46 \text{ calls/problem}
\end{equation*}
At an accuracy gain of +51.4 percentage points, this is approximately $4.46 / 51.4 \approx 0.087$ additional API calls per percentage point gained---highly cost-effective.
SIV introduces \emph{zero} additional API calls, meaning any problems it correctly verifies (skipping SHT) \emph{reduce} the average call count.
\subsection{Limitations}
\paragraph{Sample size.}
Experiments use $n=37$ and $n=10$ problems, limited by the Groq free-tier budget.
While results are internally consistent, statistical significance testing and confidence intervals are not reliable at these sample sizes.
Larger-scale evaluation is essential to confirm per-benchmark trends.
\paragraph{Blueprint bottleneck.}
The 37.8\% empty-blueprint failure rate caps MAS-SHT's theoretical accuracy at approximately 62\% even with perfect downstream processing---the per-benchmark results are consistent with this ceiling.
\paragraph{SIV evaluation in progress.}
The Symbolic Inverse Verification module was integrated in v10.0, after the cloud experiments reported here, so SIV metrics are absent from the Experiment~1 and~2 logs.
The $n{=}150$ pilot (\Cref{sec:pilot_diagnosis}) produced the first populated SIV telemetry (58/150 problems with audit data; SIV-verified answers 73.3\% accurate vs.\ 53.5\% for unverified), but under the pre-v12 selection layer this signal was frequently discarded before it could help.
The v12.0 validation run (\Cref{sec:v12_validation}) confirmed the signal is trustworthy once acted upon---SIV-verified answers were 100\% correct (12/12) against 65.9\% for unverified---though 11 of those 12 fall in the degenerate single-given regime, which is why the coverage push of Phase~B was necessary before the claim could carry weight.
Phase~B (\Cref{sec:v13}) has since closed the coverage precondition (72.7\% of problems audited) and sharpened the signal's characterization with real multi-variable material: SIV verification is highly reliable as a cross-validator (22/22 with baseline agreement) and unreliable as a standalone authority (2/14 against it).
The \emph{causal} measurement has since run (\Cref{sec:v14_routing}): as an arbitration signal SIV is causally neutral (72.0\% vs.\ 72.7\%, McNemar $p{\approx}1$), and the diagnosis---the certificate--difficulty confound---relocates SIV's measured value to compute routing (+6.9 points on the routed stratum, 63\% of wall time reclaimed) and to the in-loop repair trigger.
The claims that remain correlational or projected are now explicitly marked as such where they appear: the v15 blueprint-accuracy gains are measured on stored blueprints offline, and their end-to-end effect awaits the v15.2 GPU run.
Two further caveats: each full-run figure rests on a single run and seed, and the PAL baseline on the Phase~B mix is incomplete (its GSM-Hard block only), so the PAL comparison on that mix is provisional.
\paragraph{Benchmark scope.}
All five benchmarks are arithmetic word problems.
Extension to algebra, geometry, combinatorics, probability, and calculus requires structural modifications to the blueprint schema (e.g., supporting inequality constraints, symbolic unknowns, or set-theoretic operations).
\paragraph{Model coupling.}
All Experiment 1 roles use Qwen3-32B.
The prediction that a stronger JSON-following model in the Mathematician role would reduce the empty-blueprint rate has since been borne out in the local track: the \textit{qwen\_math7b\_mixed} preset (jointly with the reweighted mix) cut empty blueprints from 62.7\% to 27.3\% (\Cref{sec:v13}).
That change, however, was deliberately bundled with the dataset reweighting, so the preset's isolated contribution is not separately measured; and the heterogeneous \emph{cloud} presets (\Cref{sec:heterogeneous}) remain systematically unevaluated.
\paragraph{Metamorphic testing.}
The optional metamorphic testing module (\Cref{app:metamorphic}) was disabled in all experiments to bound API costs.
It supports three assertion types---delta, ratio, and monotonic---and could provide verifiable correctness guarantees on problems with clear monotonicity properties (e.g., ``more items $\Rightarrow$ higher total'').

\section{Conclusion}
\label{sec:conclusion}
% ============================================================
We presented MAS-SHT (v15.2), a multi-agent mathematical reasoning framework combining Architect--Engineer decomposition, self-verified blueprint construction, PAL-style program-aided solving, advisory rule-based process verification, a SymPy symbolic fallback, Symbolic Inverse Verification (SIV) with an audit-triggered blueprint repair loop, and confidence-gated critic-based Structured Hypothesis Testing resolved by verification-weighted, baseline-anchored arbitration.
To extend the framework from cloud-scale models to small, locally hosted open-weight models, v11 adds two blueprint-recovery mechanisms that directly target the empty-blueprint bottleneck identified in our experiments---token-level constrained decoding and two-step chain-of-thought-to-blueprint extraction---alongside a provider-agnostic client with an in-process local-inference backend and component-level ablation switches.
Motivated by an $n{=}150$ pilot in which a free-form LLM judge scored 15\% on the problems it arbitrated (\Cref{sec:pilot_diagnosis}), v12 re-architects the selection layer around deterministic evidence: the CAS-evaluated blueprint enters the candidate pool as a zero-cost independent vote, answer groups are ranked by verifiable evidence (agreement, SIV verification, executed-code support), and the LLM judge is retained only as a tie-breaker constrained to select one presented candidate by index---it can no longer emit an answer that no solver produced.
Re-running the identical 150 problems under this redesign raised accuracy from 74.0\% to 82.7\% (+8.7 points) with the upstream solvers unchanged, and confirmed SIV's signal directly (100\% accuracy on SIV-verified answers vs.\ 65.9\% on unverified ones).
Analyzing that run's own log surfaced a second, narrower selection-layer defect---a lone-primary-vs-lone-baseline tie was being resolved by a scoring artifact rather than evidence---which v12.1 fixes by refusing to resolve genuinely uncorroborated ties structurally (\Cref{sec:v12_validation}).
The evaluation then moved to a deliberately harder, coverage-oriented configuration (GSM-Hard-weighted mix plus a heterogeneous local preset placing an instruction-tuned model on the parse-critical roles), which doubled blueprint formation and raised SIV audit coverage from $\sim$37\% to 72.7\% of problems---and thereby exposed a third round of selection-layer defects that collapsed accuracy to 57.3\% (\Cref{sec:v13}).
v13.0 responds with the \emph{do-no-harm invariant}: the system may override its own zero-shot baseline only when at least two honestly independent derivations agree, with uncorroborated fields returning the baseline verbatim, and with an audit-triggered repair loop feeding SIV's error report back to the Mathematician.
The measured result is 72.7\% on the harder mix (86.7\% on its GSM8K/SVAMP portion---above the earlier mix's 82.7\%---and 58.7\% on GSM-Hard, above CoT's 56.0\% there), with the invariant's wiring verified exactly (51/51 uncorroborated problems returned the baseline answer), and with the collapse diagnosis yielding the sharpest field characterization of SIV so far: 22/22 correct as a baseline-agreeing cross-validator, 2/14 as a standalone authority.
The MAS-NoSIV ablation then closes the causal question with a negative that becomes a finding (\Cref{sec:v14_routing}): SIV is neutral as an \emph{arbiter} because its certificate is confounded with problem difficulty---on audit-passed rows the certified answer trails the baseline on those same rows by 16.7 points---so a verifier's precision must be judged against the baseline conditioned on the certificate, not the base rate.
Repositioned as an a-priori compute router, the same free certificate gates the expensive Critic stage and yields the local track's first above-baseline result (75.3\% vs.\ 74.7\% at 86\% blueprint coverage), with the routed stratum's projected gain confirmed by measurement.
Finally, v15 grounds the remaining bottleneck in a measured mechanism: the dominant NL$\to$math defect at 7B scale is operand \emph{transcription}, not reasoning---35\% of extracted givens appear nowhere in the problem text, 68\% of those one digit from a number that does---and a deterministic, abstention-first repair (operand grounding, formula-valued givens, accessor respelling) raises blueprint accuracy on stored pretest blueprints from 44\% to 60\% on the best prompt route with zero correct blueprints broken (\Cref{sec:v15_grounding}).
The v15.2 run confirms those component projections on GPU (blueprint 20.7\%\,$\to$\,40.7\%, primary 50.0\%\,$\to$\,55.3\%, oracle 84.7\%) and localizes its own 74.0\% top line to a single vote-independence defect, closed by v15.3's grounded-premise rule: corroboration between derivations sharing a blueprint is admitted only when that blueprint's operands are verified against the problem text---measured at 76.0\% vs.\ 74.7\% with zero losses, over byte-identical candidates, though derived from that same problem set and so awaiting a fresh-seed test (\Cref{sec:v153_grounded_votes}).
SIV remains the novel verification contribution, operating in two complementary layers.
\emph{Layer~1 (Execution Audit)} detects deviations between the Programmer's computed answer and the forward evaluation of the blueprint equations---establishing execution fidelity at zero API cost.
\emph{Layer~2} inverts the symbolic chain to report which declared variables are implicated by an inconsistency, enabling Critic repair that is targeted at the load-bearing variables rather than blind re-generation.
A controlled fault-injection evaluation (\Cref{sec:siv_fault_injection}) establishes the honest scope of this layer, correcting an earlier, stronger claim: it never misses the true fault (100\% recall) and reliably excludes distractors (100\%), but does not isolate a single culprit once 2+ givens are used (precision $=1/n_{\text{used}}$)---a structural consequence of every blueprint collapsing to one scalar equation, not an implementation defect.
An explicit, documented scope limitation distinguishes SIV from LLM-based backward verification \citep{jiang2024fobar}: SIV operates exclusively on the execution layer (math$\to$math) and cannot detect NL$\to$math translation errors. The two methods are orthogonal and complementary.
On a challenging mixed-benchmark set where a 32B zero-shot baseline achieves only 5.4\% accuracy, MAS-SHT recovers 56.8\%---a gain of +51.4 percentage points---with zero damage cases and zero false regressions on easier problems.
The most important empirical finding is that \emph{code execution success implies 100\% accuracy}: the entire performance gap between the framework and the baseline is explained by blueprint construction failures, pinpointing the Mathematician stage as the sole bottleneck.
Future work should prioritize: (1)~an \emph{out-of-sample} evaluation of the v15.3 grounded-premise rule on a fresh draw under a different seed. Both v15.2 and v15.3 were measured on the same fixed 150-problem set under greedy decoding, so the confirming run reproduces the earlier candidates exactly---ideal for isolating a selection rule, useless for establishing that the rule transfers. Everything else on this list is secondary to that measurement; (2)~closing the gap between the repair trigger's detection quality (80.3\% recall, zero false alarms) and its LLM fix success (15.4\%), for which the deterministic repair classes of \Cref{sec:v15_grounding} are the measured first installment (19/25 of the structural failures in the v14.0 run were mechanical, not conceptual); (3)~recovering partial fault \emph{isolation} in Layer~2 by grounding each \emph{reconstructed} given value against the problem text---the $1/n_{\text{used}}$ precision bound (\Cref{sec:siv_fault_injection}) arises from purely algebraic inversion, and v15's forward-direction grounding results make the backward-direction analogue considerably more promising than when first proposed; (4)~combining SIV with an NL-layer verifier (e.g., FOBAR-style) to cover both error layers; (5)~completing the PAL baseline on the Phase~B mix, isolating the mixed preset's contribution from the dataset reweighting (the two were deliberately bundled in Phase~B), and systematically evaluating the heterogeneous \emph{cloud} presets; and (6)~larger-scale, multi-seed evaluation to establish statistical significance of the per-benchmark results, of the +0.67-point v14.8 margin, and of the $n{=}25$ prompt-route comparison, all currently single-run and underpowered.
We believe that the four central design principles of MAS-SHT---program-aided solving cross-checked against an independently constructed declarative blueprint, critic-based peer review over parallel resampling, deterministic CAS-based verification with evidence-first arbitration in which LLM judgment is confined to evidence ties, and a do-no-harm anchor under which no amount of internal self-consistency may override an independent baseline without corroboration---are broadly applicable beyond arithmetic word problems and represent a productive direction for LLM reasoning reliability research.

\section{Confidence Gate Decision Logic}
\label{app:gate}
\begin{algorithm}[H]
\caption{Confidence Gate (v12.0). Baseline disagreement is checked \emph{before} any SIV-driven skip (v10.1 ordering invariant); a negative answer triggers SHT only when no baseline cross-check exists (v12).}
\label{alg:gate}
\begin{algorithmic}[1]
\Require Primary answer $a_p$, Baseline answer $a_b$, Programmer response $r$, Blueprint $B$, SIV result $\sigma$
\Ensure Boolean \texttt{is\_confident}, reason string
\If{$a_p = $ ``unknown''}
    \State \Return \textsc{False}, \texttt{programmer\_failed}
\EndIf
\State $b_{\text{failed}} \gets (a_b = \text{``unknown''})$
\If{\textbf{not} $b_{\text{failed}}$}
    \If{$a_p$ and $a_b$ are numeric \textbf{and} $|a_p - a_b| > 10^{-3}$}
        \State \Return \textsc{False}, \texttt{baseline\_disagreement}
        \Comment{Runs BEFORE SIV skip: only translation-layer check}
    \ElsIf{$a_p$ or $a_b$ are non-numeric \textbf{and} $a_p \neq a_b$}
        \State \Return \textsc{False}, \texttt{baseline\_disagreement}
    \EndIf
\EndIf
\If{$r.\texttt{quality\_metrics}[\texttt{"error"}] = $ ``Max attempts reached''}
    \State \Return \textsc{False}, \texttt{repair\_exhaustion}
\EndIf
\If{$\sigma \neq \textsc{None}$}
    \If{$\sigma.\texttt{invertible}$ \textbf{and} \textbf{not} $\sigma.\texttt{verified}$}
        \State \Return \textsc{False}, \texttt{siv\_inconsistency:}\texttt{failed\_givens}
        \Comment{Specific variable(s) inconsistent}
    \ElsIf{\textbf{not} $\sigma.\texttt{execution\_audit\_passed}$ \textbf{and} $\sigma.\texttt{blueprint\_answer} \neq \textsc{None}$}
        \State \Return \textsc{False}, \texttt{siv\_execution\_error}
        \Comment{Program deviates from blueprint evaluation}
    \EndIf
\EndIf
\If{$a_p < 0$ \textbf{and} $b_{\text{failed}}$}
    \State \Return \textsc{False}, \texttt{negative\_answer\_unverified}
    \Comment{v12: agreed negatives are evidence, not anomalies}
\EndIf
\State $M \gets \max\{|v| \mid v \in B.\texttt{givens},\ v \in \mathbb{R}\}$
\If{$|a_p| > 10^4 \cdot M$ \textbf{and} $M > 0$}
    \State \Return \textsc{False}, \texttt{magnitude\_anomaly}
\EndIf
\If{$b_{\text{failed}}$}
    \State \Return \textsc{False}, \texttt{baseline\_also\_failed}
\EndIf
\If{$\sigma \neq \textsc{None}$ \textbf{and} $\sigma.\texttt{execution\_audit\_passed}$ \textbf{and} $\sigma.\texttt{verified}$ \textbf{and} $\sigma.\texttt{confidence} \geq 0.90$}
    \State \Return \textsc{True}, \texttt{siv\_execution\_consistent}
    \Comment{Cross-validated: baseline agrees AND symbolically verified}
\EndIf
\State \Return \textsc{True}, \texttt{all\_criteria\_passed}
\end{algorithmic}
\end{algorithm}
\section{Triage Algorithm}
\label{app:triage}
\begin{algorithm}[H]
\caption{Majority-Vote Triage with Evidence Escalation and Baseline Anchor (v13.0). $\mathrm{hv}(G)$ denotes \emph{honest votes}: $|G|$, minus one when $G$ contains both \texttt{primary} and \texttt{blueprint\_eval}---one derivation observed twice, since they can only co-group when the execution audit certifies the code computed those very equations (\Cref{sec:do_no_harm}).}
\label{alg:triage}
\begin{algorithmic}[1]
\Require Candidate list $C$ (primary, baseline at conf.~0.5, blueprint CAS evaluation, $\leq 2$ alternatives)
\Ensure Winning answer, strategy name, resolution method
\State $V \gets \{c \in C \mid c.\texttt{code\_success} = \textsc{True} \land c.\texttt{parsed\_answer} \neq \textsc{None}\}$
\If{$V = \emptyset$}
    \State \Return (\textsc{None}, \textsc{None}, \texttt{no\_valid\_candidates})
\EndIf
\State Group $V$ by numeric answer value, tolerance $\epsilon = 10^{-3}$
\State Sort groups by $\bigl(\mathrm{hv},\ \overline{\text{confidence}}\bigr)$ descending
\State $G_1 \gets$ top group; \quad $G_2 \gets$ second (if exists)
\If{only one group}
    \State \Return $\bigl(G_1[0].\texttt{answer},\ G_1[0].\texttt{strategy},\ \texttt{unanimous}\bigr)$
\ElsIf{$\mathrm{hv}(G_1) \geq 2$ \textbf{and} $\mathrm{hv}(G_1) > \mathrm{hv}(G_2)$}
    \State \Return $\bigl(G_1[0].\texttt{answer},\ G_1[0].\texttt{strategy},\ \texttt{majority}\bigr)$
\Else
    \State Rank groups by evidence tuple $\bigl(\mathrm{hv},\ \text{SIV-verified},\ \text{executed},\ \text{primary},\ \text{baseline}\bigr)$
    \If{$\mathrm{hv}$ of top-ranked group $< 2$}
        \Comment{No corroborated group anywhere: do-no-harm invariant}
        \If{baseline candidate has a valid parsed answer}
            \State \Return $\bigl(\text{baseline}.\texttt{answer},\ \texttt{baseline\_do\_no\_harm},\ \texttt{baseline\_default}\bigr)$
        \Else
            \State \Return deterministic fallback (executed primary $\to$ any valid), \texttt{fallback}
        \EndIf
    \ElsIf{strict lexicographic winner exists among corroborated groups}
        \State \Return $\bigl(G^{*}.\texttt{answer},\ G^{*}.\texttt{strategy},\ \texttt{evidence}\bigr)$
    \Else
        \State Judge selects an \emph{index} among tied corroborated representatives (tag-first contract); invalid output $\Rightarrow$ deterministic fallback (baseline $\to$ executed primary $\to$ any valid)
        \State \Return $\bigl(\text{selected}.\texttt{answer},\ \text{selected}.\texttt{strategy},\ \texttt{judge}\ \text{or}\ \texttt{judge\_fallback}\bigr)$
    \EndIf
\EndIf
\end{algorithmic}
\end{algorithm}
\section{Symbolic Inverse Verification Algorithm}
\label{app:siv}
\begin{algorithm}[H]
\caption{Symbolic Inverse Verification (SIV) — Two-Layer Execution Audit}
\label{alg:siv}
\begin{algorithmic}[1]
\Require Blueprint $B$ (givens dict $G$, equations list $E$), Programmer answer $A$
\Ensure SIVResult $\sigma$ with \texttt{verifies\_translation = False} (explicit limitation)
\If{$\neg$SymPy available \textbf{or} $G = \emptyset$ \textbf{or} $E = \emptyset$}
    \State \Return SIVResult(\texttt{verified=False, confidence=0.5, verifies\_translation=False})
\EndIf
\State Declare each $g_i \in G$ as SymPy \texttt{Symbol}($g_i$, real=True)
\State $(\phi, \Sigma_G) \gets $ \textsc{BuildSymbolicChain}($E$, $G$) \Comment{Closed-form expr; $\Sigma_G$ maps name$\to$symbol}
\If{$\phi = \textsc{None}$}
    \State \Return SIVResult(\texttt{verified=False, confidence=0.4, invertible=False})
\EndIf
\vspace{2pt}
\State \textbf{--- Layer 1: Execution Audit (forward) ---}
\State $A_{\text{bp}} \gets \phi$ with all $g_i \in G$ substituted numerically; evaluate
\State $\varepsilon_{\text{exec}} \gets |A_{\text{bp}} - A| \,/\, \max(|A|, 10^{-9})$
\State $\texttt{exec\_passed} \gets (|A_{\text{bp}} - A| < 10^{-6})$ \textbf{or} $(\varepsilon_{\text{exec}} < 10^{-4})$
\If{\textbf{not} \texttt{exec\_passed}}
    \State \textit{// Programmer deviated from blueprint; Layer 2 will localize}
\EndIf
\State \texttt{unused\_givens} $\gets \{g_i \in G \mid \Sigma_G[g_i] \notin \phi.\text{free\_symbols}\}$
\vspace{2pt}
\State \textbf{--- Layer 2: Fault Localization (inverse) ---}
\State $m \gets 0$, \; $s \gets 0$, \; $\text{failed} \gets []$
\ForAll{$(g_i, v_i) \in G$}
    \If{$g_i \in $ \texttt{unused\_givens}}
        \State \textbf{continue} \Comment{Not solvable; excluded from denominator}
    \EndIf
    \State $s \gets s + 1$
    \State $\phi' \gets \phi$ with all $g_j \neq g_i$ substituted by their numeric values
    \State $\mathcal{R} \gets $ \textbf{SymPy.solve}($\phi' = A$, $\Sigma_G[g_i]$)
    \State $\mathcal{R}_{\mathbb{R}} \gets \{$\textbf{float}$(r) \mid r \in \mathcal{R},\ r \in \mathbb{R}\}$ \Comment{All real roots — no circular selection}
    \If{$\mathcal{R}_{\mathbb{R}} = \emptyset$}
        \State $\text{failed}.\text{append}(g_i)$; \textbf{continue}
    \EndIf
    \State \texttt{ambiguous} $\gets |\mathcal{R}_{\mathbb{R}}| > 1$
    \State \texttt{match} $\gets \exists\, r \in \mathcal{R}_{\mathbb{R}} : |r - v_i| < 10^{-4} \cdot \max(|v_i|, 10^{-9})$
    \If{\texttt{match}}
        \State $m \gets m + 1$
    \Else
        \State $\text{failed}.\text{append}(g_i)$
    \EndIf
\EndFor
\State $c \gets m \,/\, \max(s, 1)$; \quad $c \gets \min(c,\ 0.97)$ \Comment{Cap: NL$\to$math layer untested}
\State \texttt{verified} $\gets (c \geq 0.90)$ \textbf{and} \texttt{exec\_passed}
\State \Return SIVResult(
    \texttt{execution\_audit\_passed}=\texttt{exec\_passed},
    \texttt{blueprint\_answer}=$A_{\text{bp}}$,
    \texttt{execution\_rel\_error}=$\varepsilon_{\text{exec}}$,
    \texttt{verified}=\texttt{verified}, \texttt{confidence}=$c$,
    \texttt{givens\_matched}=$m$, \texttt{givens\_total}=$|G|$,
    \texttt{failed\_givens}=failed,
    \texttt{unused\_givens}=\texttt{unused\_givens},
    \texttt{invertible}=$(s > 0)$,
    \texttt{verifies\_translation}=\textsc{False},
    \texttt{computed\_answer}=$A$)
\end{algorithmic}
\end{algorithm}
\section{SymPy Symbolic Solver}
\label{app:sympy}
\begin{algorithm}[H]
\caption{SymPy Symbolic Solver (both invocation points)}
\label{alg:sympy}
\begin{algorithmic}[1]
\Require Blueprint $B$ (givens dict $G$, equations list $E$)
\Ensure (success, answer, trace)
\If{$E = \emptyset$}
    \State \Return (\textsc{False}, ``unknown'', ``No equations in blueprint'')
\EndIf
\State $\textit{ns} \gets \{k \mapsto v \mid (k,v) \in G,\ v \in \mathbb{R}\}$ \Comment{Numeric namespace}
\State $\textit{ns}[\texttt{givens}] \gets G$; \quad $\textit{last} \gets \textsc{None}$
\State $\textit{safe} \gets \{\texttt{abs}, \texttt{round}, \texttt{int}, \texttt{float}, \texttt{sqrt}, \texttt{ceil}, \texttt{floor}, \pi, \ldots\}$
\ForAll{$\textit{eq} \in E$}
    \State \textbf{attempt} Python \texttt{exec}($\textit{eq}$, safe, $\textit{ns}$)
    \If{success}
        \State $\textit{last} \gets \textit{ns}[\text{lhs}(\textit{eq})]$
    \Else
        \State $\textit{rhs} \gets \text{substitute known values into rhs}(\textit{eq})$
        \State $v \gets $ \textbf{SymPy} \texttt{parse\_expr}($\textit{rhs}$).\texttt{evalf()}
        \If{$v \neq \textsc{None}$}
            \State $\textit{ns}[\text{lhs}(\textit{eq})] \gets v$; \quad $\textit{last} \gets v$
        \Else
            \State \Return (\textsc{False}, ``unknown'', trace)
        \EndIf
    \EndIf
\EndFor
\State $a \gets \textit{ns}.\texttt{get}(\texttt{answer},\ \textit{last})$
\State \Return (\textsc{True}, \texttt{float}($a$), trace)
\Comment{Conf.\ 0.8 (post-Programmer) or 0.75 (post-Verification)}
\end{algorithmic}
\end{algorithm}
\section{Metamorphic Testing Module}
\label{app:metamorphic}
The optional metamorphic testing module verifies solution logic by perturbing input values and checking whether the output changes as expected.
When enabled, the Mathematician can include a \texttt{metamorphic\_tests} array in its blueprint, each test specifying:
\begin{itemize}[leftmargin=*,itemsep=2pt]
    \item \texttt{mutations}: a list of variable perturbations, each with fields \texttt{var} (variable name in \texttt{givens}), \texttt{op} (\texttt{"add"} or \texttt{"mul"}), and \texttt{value} (scalar).
    \item \texttt{assert}: an object with \texttt{type} and \texttt{value} specifying the expected output change.
    Three assertion types are supported:
    \begin{itemize}[leftmargin=2em,itemsep=0pt]
        \item \textbf{delta}: $|(\hat{y}_\text{mutated} - \hat{y}_\text{base}) - v| < 10^{-6}$, verifying an exact additive change.
        \item \textbf{ratio}: $|(\hat{y}_\text{mutated} / \hat{y}_\text{base}) - v| < 10^{-4}$, verifying a proportional change.
        \item \textbf{monotonic}: $\hat{y}_\text{mutated} > \hat{y}_\text{base}$ or $< \hat{y}_\text{base}$, verifying direction of change.
    \end{itemize}
\end{itemize}
For each test, the solver creates a mutated copy of the \texttt{givens} dictionary by applying the mutations, re-executes the original code with the mutated givens, and evaluates the assertion.
A single failing assertion disqualifies the code answer and triggers SHT.
The module was disabled in all experiments presented in this paper to bound API and execution costs.
\section{Error Response Detection}
\label{app:error_detection}
The \texttt{\_is\_error\_response()} function is applied at every point where a numeric answer is extracted from an LLM response.
It returns \textsc{True} (indicating an error, not a mathematical answer) under any of the following conditions:
\begin{enumerate}[leftmargin=*,itemsep=2pt]
    \item The response is \textsc{None} or the empty string.
    \item The response starts with \texttt{ERROR\_} (covering \texttt{ERROR\_GENERATION}, \texttt{ERROR\_AUTH\_401}, \texttt{ERROR\_AUTH\_403}, \texttt{ERROR\_RATE\_LIMIT\_DAILY}, \texttt{ERROR\_BUDGET\_EXCEEDED}).
    \item The response (case-insensitive) matches any of the following patterns: HTTP status codes 401/403/429/500/502/503 preceded by ``error''; the words ``unauthorized'', ``forbidden'', ``rate~limit'', or ``internal~server''; ``authentication failed/error/invalid''; ``api key invalid/missing/expired''; ``token limit reached/exceeded''; or ``budget exceeded''.
    \item The response is shorter than 5 characters and does not match a standalone number pattern.
\end{enumerate}
This guard is particularly important for preventing HTTP status codes returned during API failures (e.g., a 401 response parsed as the answer ``401.0'') from being recorded as correct answers.
\section{Blueprint JSON Schema for Constrained Decoding}
\label{app:schema}
The schema below is compiled into a token-level acceptor (\texttt{lm-format-enforcer}) and supplied to the local-inference generation loop as a \texttt{prefix\_allowed\_tokens\_fn} (\Cref{sec:blueprint_recovery}).
The \texttt{reasoning} field is listed first and marked required so that the model produces a free-text scratchpad \emph{before} it is constrained to emit the structured fields; \texttt{givens} is constrained to a numeric-valued object and \texttt{equations} to an array of strings.
\begin{lstlisting}[language=Python,caption={Blueprint schema (v11.1) used for token-level constrained decoding on the \texttt{local\_hf} backend.}]
_BLUEPRINT_SCHEMA = {
    "type": "object",
    "properties": {
        "reasoning":       {"type": "string"},
        "unknown":         {"type": "string"},
        "givens":          {"type": "object",
                            "additionalProperties": {"type": "number"}},
        "equations":       {"type": "array",
                            "items": {"type": "string"}},
        "expected_answer": {"type": "string"},
    },
    "required": ["reasoning", "givens", "equations", "expected_answer"],
}
\end{lstlisting}
\section{SIV Evaluation Module}
\label{app:siv_eval}
The SIV-specific results of Experiment~3 are produced by a standalone analysis module that consumes the per-problem run logs (which already record the \texttt{siv\_*} columns) and emits one tidy table per research question, without any model or network access.
It computes five tables:
\begin{enumerate}[leftmargin=*,itemsep=2pt]
    \item \textbf{Coverage funnel}: the attrition from total problems $\to$ non-empty blueprint $\to$ SIV-audited $\to$ symbolically invertible $\to$ verified. This quantifies how often the inspector actually had a blueprint to check---the truth check for whether SIV is starved on a given model.
    \item \textbf{Detector metrics}: treating the SIV verdict (Layer~1 execution audit, and the Layer~2 \texttt{verified} flag) as a binary correctness detector, the confusion matrix and derived precision, recall, specificity, and false-positive rate. The false-positive cell isolates exactly the translation-layer errors SIV is blind to by design.
    \item \textbf{Error-layer decomposition}: among SIV-audited wrong answers, the split into execution-layer (SIV-detectable), translation-layer (NL$\to$math, SIV-blind), and non-invertible (SIV abstained). This is the empirical instantiation of the scope claim of \Cref{sec:siv}.
    \item \textbf{Confident-skip efficacy}: accuracy and average LLM-call count for the SIV-confident-skip group versus the went-to-SHT group, quantifying the cost saved without accuracy loss.
    \item \textbf{Ablation}: the accuracy and cost delta between the full system and MAS-NoSIV, with a McNemar test on the paired per-problem outcomes.
\end{enumerate}
Because ``SIV ran'' cannot be read from a single column (a non-invertible chain leaves the audit verdict null even though SIV executed), the module detects it as the disjunction of three signals: a non-null invertibility flag, a non-null execution-audit verdict, or a positive given count.
